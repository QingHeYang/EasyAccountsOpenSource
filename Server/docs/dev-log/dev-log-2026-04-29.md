### 1. AI API 业务说明文档（新增）

#### 背景

主管反馈 AI 端 LLM 调用后端工具时准确率不高，原因是 AI 端的工具 docstring 与后端实际行为有偏差。主管让我列出 AI 端在调的 9 个接口（6 读 + 3 写）并配合产品语义说明，给 AI 端 Claude 重写提示词参考。

| 接口 | AI 工具 |
|---|---|
| GET `/account/getAccount` | accounts |
| GET `/type/getType` | types |
| GET `/action/getAction` | actions（仅内部用） |
| GET `/home/getHomeInfoV2/{year}` | year_statistics |

#### 调研过程

逐个挖 Controller / Service / DTO / Entity / Repository / SQL Provider，整理出每个接口的：
- 业务定位（用户从哪个 UI 入口能触发）
- 核心实体的产品定义（account / action / type / handle / collect / from / note）
- 入参字段语义、默认值、合法取值、字段间约束
- 特殊业务规则（type 与 action 的 N:1 关系、handle 三态、转账场景的 accountToId 必填、统计口径是否含转账等）
- 返回字段含义、错误场景

#### 给 AI 端纠正的几个理解错误

挖代码过程中发现 AI 端目前对几个接口的理解与实际行为有偏差，文档里专门写了一节「docstring 重写建议」：

1. **`make_excel` 不返回下载 URL**：实际是生成 Excel 文件后通过邮件附件发送。AI 端文档说"返回 downloadUrl"完全错误，客户端只能拿到 `{ success: bool, log: string }` 字符串组合
2. **`types` 工具的"父分类是否可记账"判断错了**：当前 AI 端的判断是"一级分类有子分类则不可用"，但后端实际规则是"父分类有子分类 + 父分类 actionId 不为 null 才不可用"。actionId 为 null 的"通用容器"父分类是合法可记账的
3. **`update_flow` 不传 `from` 会被置空**：FlowService 第 154-156 行有兜底 `if (from == null) from = ""`。AI 端 update 时若不想动 from，必须先 GET 原值再传回
4. **`getFlowByScreen` 的 `chooseHandle=3` 才是"全部"**：传 0 仅看收入，AI 端容易传错
5. **types/actions 多选的逻辑**：组内 OR、组间 AND；选父分类自动覆盖其全部子分类的流水
6. **totalIn/totalOut/totalEarn 不含转账**：handle=2 的转账记录会出现在 flows 列表，但 totalIn/totalOut 都是 0
7. **鉴权 header 不带 Bearer 前缀**：直接是 token 字符串本身，加了前缀会鉴权失败

#### 顺带发现的两个未修问题（暂记录在文档里）

- **`home/getHomeInfoV2` 年度/月度统计口径小不一致**：`yearIncome/yearOutCome` 走 MyBatis SQL `SUM(CASE WHEN handle)` 不过滤 `fDisable`；`monthDetails` 走 JPA 在 Java 层算过滤 `fDisable`。当前 `fDisable` 字段没有产品入口能切换所以表现一致，但将来若加"软删除流水"功能，年合计 ≠ 月合计相加
- **`getFlowByScreen` 的 N+1 查询**：第 98-100 行每条流水都单独 `imageService.getFlowImages(flowId)` 查一次"是否有图"，一个月 200 条流水就是 200 次额外 DB 查询。流水量大的老用户会感到列表加载变慢

这两点已记录在主管汇报里，等主管拍板是否本期修。

### 2. 修复 Bug · 删流水留下图片孤儿

#### 问题描述

`flow` 与 `flow_image` 是 1:N 独立表设计，DB 层只有索引没有外键约束（`yd_jz_2.5.0.yaml:42-46`），所以删流水时不会数据库级联删 flow_image。检查 `FlowService.doDeleteFlow` 发现：

```java
// 修改前
public void doDeleteFlow(int id) throws Exception {
    // ...账户余额回滚...
    flowDao.deleteFlowById(id);   // 只删 flow 表，flow_image 不动
}
```

后果：
- `flow_image` 表里残留孤儿记录（flow_id 指向已删除的 flow）
- `/Ledger/images/` 磁盘上对应的图片文件也不删
- 长期累积导致 DB 表膨胀 + 磁盘占用增长

同样问题在 `doUpdateFlow` 也存在 —— 旧代码用「先删后加」清 DB 关联但完全不动磁盘文件，编辑流水时移除某张图后磁盘文件就成孤儿。

#### 解决方案

`ImageService` 加 3 个语义清晰的方法 + 1 个私有 helper：

| 方法 | 用途 | DB 关联 | 磁盘文件 |
|---|---|---|---|
| `deleteFlowImages(flowId)` | 旧方法，保留 | 删 | **不删**（避免误删被复用的图） |
| `deleteFlowImagesAndFiles(flowId)` | 删流水时用 | 删 | 全删 |
| `replaceFlowImages(flowId, newNames)` | 编辑流水时用 | 全删后重写 | 按 diff 删（旧 - 新 = 被移除的） |
| `deleteImageFileQuietly(fileName)` | 私有 helper | - | 单文件删 + canonical 路径校验 |

为什么 `deleteFlowImages` 保留不动磁盘的旧语义：编辑流水时客户端传的是「最终图片列表」，里面可能有保留的旧图。如果"先删 DB"时连磁盘也删了，再去 saveFlowImages 时这些 fileName 对应的磁盘文件已经没了 —— 客户端展示会全部 404。所以编辑场景必须用 `replaceFlowImages` 走 diff 路径。

#### 代码实现

`ImageService.java`：

```java
/**
 * 删除流水关联 + 物理清理被遗弃的磁盘文件
 * 给 doDeleteFlow 使用：流水彻底删除时，关联的图片也不再有任何引用
 */
@Transactional
public void deleteFlowImagesAndFiles(Integer flowId) {
    List<FlowImage> existing = flowImageRepository.findByFlowId(flowId);
    flowImageRepository.deleteByFlowId(flowId);
    for (FlowImage img : existing) {
        deleteImageFileQuietly(img.getImageName());
    }
}

/**
 * updateFlow 时按 diff 清理被移除的图片：
 * - 旧关联里有但新关联里没有 → DB + 磁盘都清
 * - 都有的（复用）→ 不动
 */
@Transactional
public void replaceFlowImages(Integer flowId, List<String> newImageNames) {
    List<FlowImage> oldImages = flowImageRepository.findByFlowId(flowId);
    Set<String> retained = (newImageNames == null) ? Collections.emptySet()
            : new HashSet<>(newImageNames);

    flowImageRepository.deleteByFlowId(flowId);

    for (FlowImage img : oldImages) {
        if (!retained.contains(img.getImageName())) {
            deleteImageFileQuietly(img.getImageName());
        }
    }

    if (newImageNames != null) {
        saveFlowImages(flowId, newImageNames);
    }
}

/**
 * 物理删除单个图片文件，失败仅记日志
 * 仅允许在 uploadPath 之下，防止异常 fileName 造成误删
 */
private void deleteImageFileQuietly(String fileName) {
    if (fileName == null || fileName.isEmpty()) {
        return;
    }
    try {
        File baseDir = new File(uploadPath).getCanonicalFile();
        File target = new File(baseDir, fileName).getCanonicalFile();
        if (!target.toPath().startsWith(baseDir.toPath())) {
            log.warn("拒绝删除越界路径文件: {}", fileName);
            return;
        }
        if (target.exists() && target.isFile() && !target.delete()) {
            log.warn("图片文件删除失败: {}", target.getAbsolutePath());
        }
    } catch (IOException e) {
        log.warn("图片文件删除异常 fileName={}: {}", fileName, e.getMessage());
    }
}
```

`FlowService.doDeleteFlow`：

```java
accountService.updateOriginAccount(lastAccount);
// v2.7.0: 删流水时清理图片关联 + 磁盘文件，避免 flow_image 表与 uploads 目录孤儿
imageService.deleteFlowImagesAndFiles(id);
flowDao.deleteFlowById(id);
```

`FlowService.doUpdateFlow`（替换原"先删后加"）：

```java
// v2.7.0: 更新图片关联，按 diff 清理被移除的磁盘文件（避免编辑时去掉的图片留孤儿）
imageService.replaceFlowImages(id, flowAddRequestDto.getImages());
```

#### 兼容性

- 纯收尾逻辑，不影响业务流程
- 老用户升级无感，已有的孤儿数据不会自动清理（需要主管决定要不要写一次性数据迁移脚本）
- `deleteImageFileQuietly` 内部用 `getCanonicalFile()` + `toPath().startsWith()` 双保险，即使数据库里被注入异常 fileName 也不会误删

### 3. 修复 Bug · 图片下载接口路径穿越漏洞

#### 问题描述

`GET /image/{fileName}` 接口为了让浏览器直接 `<img src="...">` 加载，被设计为**不需要鉴权**（在 `WebConfig.excludePathPatterns` 中）。但接口实现里：

```java
// 修改前
File file = new File(uploadPath + fileName);  // 直接拼接，无校验
```

`fileName` 来自 `@PathVariable`，理论上恶意 URL 如 `/image/..%2F..%2Fconfig%2Fsecret.key` 经 servlet 解码后会拼成 `/Ledger/images/../../config/secret.key`，访问到服务器上的其他文件。

**当前实际不可利用**：fileName 由后端 ImageService.uploadImage 生成（时间戳 + 随机数），客户端正常调用拿不到含路径分隔符的 fileName。但接口本身校验缺失，安全审计角度是漏洞，且与开源版本的"任何人都能搭建"场景相关 —— 黑客直接构造 URL 即可绕过客户端。

#### 解决方案

双层防御：
1. **字符白名单**：`^[A-Za-z0-9._-]{1,100}$`，禁止任何路径分隔符 / `..` / 编码字符 / 中文等。后端生成的 fileName 形如 `1714123456_8923.jpg` 完全在白名单内
2. **路径规范化校验**：用 `getCanonicalFile()` 拿到真实路径，再用 `toPath().startsWith(baseDir.toPath())` 确保不会越界。即使白名单被绕过（比如 Java URL 解码漏洞）也会被这层挡住

#### 代码实现

```java
// v2.7.0: 文件名白名单：字母数字 + . _ -，长度 ≤ 100（与 DB 列长度一致）
// 后端生成的 fileName 形如 "1714123456_8923.jpg"，不会含 / \ : ..
// 此正则用于挡住任何客户端构造的恶意 fileName
private static final java.util.regex.Pattern SAFE_FILENAME =
        java.util.regex.Pattern.compile("^[A-Za-z0-9._-]{1,100}$");

@Operation(summary = "获取图片")
@GetMapping("/{fileName}")
public ResponseEntity<Resource> getImage(@PathVariable String fileName) {
    try {
        // 1. 字符白名单：禁止任何路径分隔符 / .. 等
        if (fileName == null || !SAFE_FILENAME.matcher(fileName).matches()) {
            log.warn("拒绝非法 fileName: {}", fileName);
            return ResponseEntity.notFound().build();
        }

        // 2. 路径规范化：确保最终路径在 uploadPath 之下，挡住 URL 解码后的越界
        File baseDir = new File(uploadPath).getCanonicalFile();
        File target = new File(baseDir, fileName).getCanonicalFile();
        if (!target.toPath().startsWith(baseDir.toPath())) {
            log.warn("拒绝越界路径访问: {} -> {}", fileName, target.getAbsolutePath());
            return ResponseEntity.notFound().build();
        }
        if (!target.exists() || !target.isFile()) {
            return ResponseEntity.notFound().build();
        }

        Resource resource = new FileSystemResource(target);
        // ...原有 Content-Type 判断逻辑不变...
    }
}
```

#### 兼容性

- 合法 fileName（后端生成的格式）100% 通过
- 非法 URL 一律返回 404（不暴露"为什么失败"，避免给攻击者反馈）

## 遇到的坑 / 注意事项

### 1. 编辑流水时不能简单"先删 DB + 删磁盘 + 重建"

最初想法是直接在 `deleteFlowImages` 里同时删磁盘，但这样会破坏编辑场景：

- 用户编辑流水保留了部分旧图（比如原有 3 张，删了 1 张保留 2 张，这 2 张的 fileName 还在 update 入参里）
- 如果删 DB 的同时把磁盘文件也删了，新的 saveFlowImages 重写关联时这 2 张文件已经不在了
- 客户端拿到 fileName 去 GET /image 时全部 404

正确做法：编辑场景走 diff（旧 - 新 = 被移除的，只删这部分磁盘），删流水场景全删。两个语义分别对应 `replaceFlowImages` 和 `deleteFlowImagesAndFiles`。

### 2. 路径穿越校验要用 canonical path，不能光做字符串替换

之前见过的"安全代码"是做 `if (fileName.contains(".."))`，但这种方式可以被绕过：
- URL 编码：`..%2F..%2F` → 经 servlet 解码后变成 `../../`
- Unicode 编码：`%c0%ae%c0%ae`（OWASP 经典案例）
- Windows 路径：`..\\..\\config`

唯一可靠做法是 `getCanonicalFile()` 拿到 OS 解析后的真实路径，再判断是否在允许的目录之下。

### 3. AI API 文档不能只写技术契约

主管要的是「产品语义」，不是 Swagger 复制粘贴。比如 `chooseHandle` 字段，技术契约只会说"int，0-3"，但产品语义要写：
- 0 = 只看收入（不是默认值）
- 1 = 只看支出
- 2 = 只看转账
- 3 = 全部
- AI 端最容易传错的是把 0 当成"全部"

文档里给 AI 端的「docstring 重写建议」一节就是按这种"产品语境 + 容易踩坑点"的视角写的，不是字段类型清单。
