## 今日开发内容

### 1. 修复 DTO 转换返回默认值 0 的 bug

#### 1.1 问题背景

快记模板接口 `getAllTemplates` 返回数据时，当 `type_id` 为 null（未设置分类）时，返回的 `type.id` 是 0 而不是 null。

**原因分析：**

`TypeListResponseDto.convertToDto()` 方法中，当传入的 `type` 为 null 时，直接返回 `this`（一个新创建的空对象）。由于 `id` 字段是基本类型 `int`，默认值为 0。

```java
// 问题代码
public TypeListResponseDto convertToDto(Type type) {
    if (type == null) {
        return this;  // 返回空对象，id 默认为 0
    }
    // ...
}
```

**影响：**
- 前端收到 `type.id = 0`，可能误认为设置了分类
- 前端用 `id=0` 去查询分类详情会出错

#### 1.2 解决方案

当关联对象为 null 时，返回 null 而不是空对象。

**修改文件：**

1. `TypeListResponseDto.java`
2. `AccountResponseDto.java`

```java
// 修复后
public TypeListResponseDto convertToDto(Type type) {
    if (type == null) {
        return null;  // 改为返回 null
    }
    // ...
}
```

### 2. 修复首页统计查询因无效分类导致报错

#### 2.1 问题背景

访问首页时报错：

```
javax.persistence.EntityNotFoundException: Unable to find com.deepblue.yd_jz.entity.Type with id 0
    at com.deepblue.yd_jz.service.HomeService.getFlowsByYearGroupedByMonth(HomeService.java:165)
```

**原因分析：**

数据库中存在 `type_id = 0` 的流水记录（脏数据），JPA 查询时尝试加载关联的 Type 实体，但找不到 `id=0` 的分类记录。

#### 2.2 解决方案

修改 `FlowRepository.findByYear` 查询，排除无效分类（`type_id <= 0`）的流水，这些记录不参与首页统计。

**修改文件：** `FlowRepository.java`

```java
// 修复前
@Query("SELECT f FROM FlowJpaEntity f WHERE f.fDate LIKE CONCAT(:year, '%')")
List<FlowJpaEntity> findByYear(@Param("year") Integer year);

// 修复后
@Query("SELECT f FROM FlowJpaEntity f WHERE f.fDate LIKE CONCAT(:year, '%') AND f.typeId > 0")
List<FlowJpaEntity> findByYear(@Param("year") Integer year);
```

### 基本类型 vs 包装类型

| 类型 | 默认值 | 适用场景 |
|------|--------|----------|
| `int` | 0 | 确定有值的字段 |
| `Integer` | null | 可能为空的字段（如外键） |

**建议：** 实体类中的外键字段应使用 `Integer` 类型，避免默认值 0 被误认为有效 ID。

### 3. 新增多端登录支持

#### 3.1 需求背景

当前认证机制为单端模式：每次登录生成新 Token，会导致其他设备的 Token 失效被踢下线。

用户需求：支持多端同时登录，共享同一个 Token。

#### 3.2 设计方案

通过环境变量控制登录模式，不修改 Auth 实体结构，保持向后兼容。

**核心思路：**
- 单端模式：每次登录生成新 Token（现有逻辑）
- 多端模式：登录时复用现有 Token，只刷新过期时间

#### 3.3 环境变量

| 变量名 | 配置键 | 默认值 | 说明 |
|--------|--------|--------|------|
| `SINGLE_LOGIN` | `auth.single_login` | `true` | 是否单端登录 |

**配置示例：**

```properties
# 单端模式（默认）：新登录踢掉旧设备
auth.single_login=${SINGLE_LOGIN:true}

# 多端模式：共享Token，多设备同时在线
auth.single_login=${SINGLE_LOGIN:false}
```

#### 3.4 实现逻辑

**修改文件：** `AuthService.java`

```java
@Value("${auth.single_login:true}")
private boolean singleLogin;

public AuthDto login(String username, String password) {
    // ... 验证通过后
    long now = System.currentTimeMillis();

    if (!singleLogin && auth.getExpireTime() > now) {
        // 多端模式 + Token未过期：只刷新过期时间，不换Token
        auth.setExpireTime(now + expired * 60 * 1000);
    } else {
        // 单端模式 或 Token已过期：生成新Token
        auth.refreshToken(expired);
    }
    // ...
}
```

#### 3.5 场景说明

| 模式 | Token 状态 | 登录行为 |
|------|-----------|---------|
| 单端 (true) | 任何 | 生成新 Token，旧设备失效 |
| 多端 (false) | 未过期 | 复用现有 Token，刷新过期时间 |
| 多端 (false) | 已过期 | 生成新 Token，所有设备需重新登录 |

#### 3.6 模式切换

| 切换方向 | 影响 |
|----------|------|
| 单端 → 多端 | 现有 Token 继续有效，新登录设备共享 |
| 多端 → 单端 | 下次登录生成新 Token，其他设备失效 |

## 技术要点

### 基本类型 vs 包装类型

| 类型 | 默认值 | 适用场景 |

### 多端登录设计选择

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| Token 列表 | 可单独踢设备 | 改动大，需管理列表 | 未采用 |
| JWT 无状态 | 天然多端 | 无法主动失效 | 未采用 |
| 共享 Token | 改动最小，向后兼容 | 无法区分设备 | ✅ 采用 |

对于单用户私有部署场景，共享 Token 方案最为简洁实用。
