### 2. 8 个 bug 的定位与修复

#### 2.1 Bug #1 · `java.sql.Date.toInstant()` 抛 `UnsupportedOperationException`

**现象**：扫描器第一次执行规则就挂：
```
scheduling-1 ERROR ScheduledFlowExecuteTask - scan error: null
java.lang.UnsupportedOperationException
    at java.sql.Date.toInstant(Date.java:316)
```

**根因**：Hibernate 从 `@Temporal(TemporalType.DATE)` 列读出来是 `java.sql.Date`（`java.util.Date` 子类），它重写 `toInstant()` 强制抛异常。扫描器的 `toLocalDate(date)` 直接调 `date.toInstant()` 就中招。

**修复**：用 `getTime()` 绕过：
```java
private static LocalDate toLocalDate(Date date) {
    if (date == null) return null;
    return new java.sql.Date(date.getTime()).toLocalDate();
}
```

Task + Service 两处都改。

#### 2.2 Bug #2 · `baselineForRecompute` 每日周期跳过今天（create 路径）

**现象**：PUT 规则（`startDate=今天`，每日）→ 返回 `nextRunDate=明天`，应该是今天。

**根因**：公式 `from=today` → `CycleCalculator(DAILY, today) = today + 1 day = 明天`。"严格大于 from" 的语义把基准当天跳过了。

**修复**：`max(today, startDate) - 1`，让 next 能"落回"基准当天：
```java
LocalDate anchor = startDate.isAfter(today) ? startDate : today;
return anchor.minusDays(1);
```

#### 2.3 Bug #3 · 失效挂钩只覆盖 RUNNING 规则

**现象**：建 NOT_START 规则引用账户 X → 停用账户 X → 规则不变、accountId 仍指 X。

**根因**：`invalidateByAccount/Type` 的 SQL 写死 `status = RUNNING`；状态机 `SYS_INVALIDATE` 前置也写死 RUNNING。

**修复 3 处**：
1. Repository 查询去掉 status 过滤（INVALID 规则的 accountId/typeId 已置 null，天然不命中）
2. Service 方法改用新查询
3. 状态机前置放宽：**非 INVALID 均可**
```java
case SYS_INVALIDATE:
    if (from != STATUS_INVALID) return STATUS_INVALID;
    break;
```

副作用：状态机单测里原本的 `fromNotStart_throws` / `fromPaused_throws` 反转成合法 case。

#### 2.4 Bug #4 · 提醒扫描漏 NOT_START 规则

**现象**：新建规则 `startDate=明天, reminderEnabled=true`，设提醒到 +1 分钟，等了一分钟 `user_notice` 表仍空。

**根因**：`findRulesForReminder` 查询写死 `status = RUNNING`。但规则从 create 到 startDate 这段都是 NOT_START，提醒扫描把它漏了。

**修复**：Repository 改 `status IN :statuses`，Task 传 `[NOT_START, RUNNING]`。

#### 2.5 Bug #5 · 提醒窗口边界场景：1 天后执行 + 3 天前提醒 → 无通知

**现象**：`remindBeforeDays=3`，规则 `startDate=明天`（next=today+1）。按旧逻辑扫描找 `next = today+3`，**严格等于单点匹配**，永远不命中。

**根因**：单点匹配无法覆盖"用户刚建规则、提醒窗口已开启"的场景。

**修复（两头夹）**：
1. 查询改区间 `next_run_date ∈ [today, today+N]`
2. 新增 `ReminderService.checkAndDispatch(rule)` 单一入口（资格判断 + 防重复 + 派发）
3. `ScheduledFlowRuleService.createRule/updateRule/startRule` 末尾**立即**调一次 → 覆盖"新建/修改后即时补发"
4. 常规扫描保留：Task 每天 remind_time 那一分钟批量扫一次

```
┌────────────────────────────────────────────┐
│ ReminderService.checkAndDispatch(rule)     │
│   - reminderEnabled?                        │
│   - status 活跃?                            │
│   - nextRunDate 在 [today, today+N] 窗口?   │
│   - 未发过?                                  │
│   → 写 user_notice + 可选发邮件             │
└─────────┬──────────────────────┬───────────┘
          │                      │
  ┌───────┴────────┐     ┌───────┴─────────────┐
  │ Task 每天       │     │ Service create /    │
  │ remind_time 扫 │     │ update / start      │
  │ 区间内所有规则  │     │ 末尾调一次           │
  └────────────────┘     └─────────────────────┘
```

#### 2.6 Bug #6 · updateRule 不清旧通知

**现象**：规则 14（每月 1 号房贷）的通知里写"将于 2026-04-24 09:00:00 自动记账"，但规则 nextRunDate=2026-05-03。通知和规则对不上。

**根因**：`updateRule` save 后只调 `checkAndDispatch` 补发新通知，**没清旧通知**。用户改 cycleDates 后新旧 nextRunDate 不一致，旧通知残留。

**修复**：
```java
noticeRepo.deleteByRelatedRuleId(id);    // 先全清
reminderService.checkAndDispatch(saved); // 再基于新字段补发
```

#### 2.7 Bug #7 · advanceCursor 错过分支不清旧 runDate 通知

**现象**：规则 next=4/24 runTime=09:00，13:XX 扫描走"今天已过点"分支 → advanceCursor 推 next=5/3。但 `related_run_date=4/24` 的通知留着成了误导。

**根因**：原 `advanceCursor` 只在 `completed` 分支清通知，错过路径（markExecuted=false）不清。

**修复**：记下旧 nextRunDate，推完后精确删那一天：
```java
Date oldNextRunDate = rule.getNextRunDate();
// ... 推进 next / save ...
if (completed) {
    noticeRepo.deleteByRelatedRuleId(rule.getId());  // 全清
} else if (oldNextRunDate != null) {
    // 错过推游标路径 → 精确删旧那天
    noticeRepo.deleteByRelatedRuleIdAndRelatedRunDate(
            rule.getId(), oldNextRunDate);
}
```

成功执行路径（`executeRuleOrThrow` 内部已删过）走这里是幂等 no-op。

#### 2.8 Bug #8 · 已执行过的规则改字段时 next_run_date 回退导致丢天

**现象**：每日规则 14:14 执行成功 → `last=today, next=明天`。14:20 用户 PUT 改 runTime=14:24 → 查规则 `next` 回退到**今天**。

扫描器下一分钟：
- `last=today == today` → 分支 A 跳过 ✓ 不重复扣
- **但明天 `next=昨天 < today`** → 分支 B 推 next=后天，**不执行** ❌ 跳过了明天

每日规则本来每天 1 次，PUT 改一下 → **少扣一天**。

**根因**：`baselineForRecompute` 公式只看 today/startDate，**忽略 lastRunDate**：
```java
// Bug #2 修完后的版本（处理 create 对）
LocalDate base = startDate.isAfter(today) ? startDate : today;
return base.minusDays(1);
// 已执行过的规则没进这个公式
```

**修复**：lastRunDate 加入 floor 运算，保证 next 严格大于已执行日：
```java
LocalDate anchor = startDate.isAfter(today) ? startDate : today;
LocalDate base = anchor.minusDays(1);
if (rule.getLastRunDate() != null) {
    LocalDate lastRun = toLocalDate(rule.getLastRunDate());
    if (lastRun.isAfter(base)) {
        base = lastRun;  // 已执行过的规则的下限
    }
}
return base;
```

验证（修后）：同场景 base=lastRun=today → next=tomorrow **保持**。

### 5. note 标记格式：`【定时】` → ` #定时`

**动机**：观察现有外部来源（AI / MCP / Claw）生成的 flow，note 格式是 `原备注 #XX记账`（如 `#Claw记账`）。定时记账保持风格一致用 ` #定时`（空格+#+常用汉字）。

`【定时】` 用的全角括号在 Windows 下 javac 编码陷阱比较容易踩（实测过乱码 `【定时�\udc80\udc91`）。换成常用汉字就稳。

### 6. Windows 编码坑 + 兜底文案

Windows 默认编码 GBK 导致 javac 读 UTF-8 源文件的中文字符串时乱码。现象：
- `【定时】` → `【定时�\udc80\udc91`（全角括号踩坑）
- `[已删除]` → `[宸插垹闄]`

处理：
1. note 标记改用常规汉字 ` #定时`（实测 OK）
2. `[规则已删除]` 用半角方括号 + 常规汉字（`#定时` 验证后同理 OK）
3. IDE 编码建议 `File > Settings > Editor > File Encodings` 全部 UTF-8（用户侧一次性修）

## 技术要点

### 1. 状态机的"守门员"价值被进一步验证

Bug #3 修复时把 `SYS_INVALIDATE` 前置从"仅 RUNNING"放宽到"非 INVALID"，只改了一个 switch case 里的 if 条件。因为所有改 status 的地方都**必须**走 `transit()`，这个规则变更立即影响三个调用方（`invalidateByAccount` / `invalidateByType` / 未来可能的其他事件）。

守门员模式的收益：**规则变一次，代码改一处，调用方零改动**。

### 2. 游标 + 扫描 的调度模式暴露了两个 baseline 陷阱

Bug #2 和 Bug #8 都是 `baselineForRecompute` 的两次迭代：

| 场景 | 公式 | 问题 |
|---|---|---|
| 初版 | `startDate.isAfter(today) ? startDate-1 : today` | create 时每日规则跳过今天（Bug #2） |
| Bug #2 修后 | `max(today, startDate) - 1` | 已执行过的规则 update 时回退到 lastRun 之前（Bug #8） |
| Bug #8 修后 | `max(today-1, startDate-1, lastRunDate)` | 完整正确 |

学到：游标类系统的基准日期要同时覆盖"位置"和"历史"两个维度。

### 3. 中文字符串的编码风险

`【定时】` 踩坑、`[规则已删除]` 通过。**差异是全角括号 vs 半角括号**。根本解：IDE 文件编码统一 UTF-8 + pom.xml `<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>`。暂时以"避开全角特殊字符"作为代码层兜底。

### 4. Hibernate @NotFound(IGNORE) 让孤儿关联优雅退化

`scheduled_flow_log.rule_id` 指向已删规则时，默认 LAZY 代理访问抛 `EntityNotFoundException`。加 `@NotFound(action = NotFoundAction.IGNORE)` 返回 null，配 DTO 兜底文案，孤儿日志变"历史记录"而非崩溃点。
