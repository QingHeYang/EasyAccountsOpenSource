## 1. 跨平台命令执行

### 1.1 问题背景

备份恢复功能原先只支持 Ubuntu（Docker 环境），本地 Windows 开发时无法测试。

### 1.2 解决方案

添加 `system.os` 配置项，根据操作系统选择不同的命令执行方式：

| 操作系统 | 命令格式 |
|----------|----------|
| Windows | `cmd /c command` |
| Ubuntu | `/bin/sh -c command` |

### 1.3 代码实现

**BackupService.java / SQLBackUpTask.java：**

```java
@Value("${system.os:ubuntu}")
private String systemOs;

private String[] buildCommand(String command) {
    if ("win".equalsIgnoreCase(systemOs)) {
        return new String[]{"cmd", "/c", command};
    } else {
        return new String[]{"/bin/sh", "-c", command};
    }
}
```

### 1.4 配置变更

```properties
# Windows 本地开发
system.os=win

# Docker 环境（默认）
system.os=ubuntu
```

## 2. 文件路径空格处理

### 2.1 问题背景

用户上传的备份文件名可能包含空格（如 `yd_jz_base (1).sql`），导致命令执行失败。

### 2.2 解决方案

用引号包裹文件路径：

```java
// 修复前
String[] cmd = buildCommand(restoreCmd + filePath);

// 修复后
String[] cmd = buildCommand(restoreCmd + "\"" + filePath + "\"");
```

## 3. 错误输出捕获

### 3.1 问题背景

命令执行失败时只返回退出码，无法定位具体错误原因。

### 3.2 解决方案

捕获进程的错误输出流：

```java
StringBuilder errorOutput = new StringBuilder();
try (BufferedReader reader = new BufferedReader(
        new InputStreamReader(process.getErrorStream()))) {
    String line;
    while ((line = reader.readLine()) != null) {
        errorOutput.append(line).append("\n");
    }
}

int exitCode = process.waitFor();
if (exitCode != 0) {
    String errorMsg = errorOutput.toString().trim();
    throw new BusinessException(ErrorCode.SYSTEM_ERROR,
        "恢复失败: " + (errorMsg.isEmpty() ? "退出码 " + exitCode : errorMsg));
}
```

## 4. 恢复前清空数据库

### 4.1 问题背景

恢复旧版本备份时出现 Liquibase 迁移冲突：

**场景分析：**

```
恢复前（v2.6.0）                    恢复旧备份后
========================           ========================
account (有 account_type)    →     account (旧结构，被覆盖)
flow_image (v2.5.0 新增)     →     flow_image (未被覆盖！)
databasechangelog (16条)     →     databasechangelog (被覆盖/空)
```

**问题根源：**

旧备份使用 `mysqldump` 不带 `--databases` 参数，只会 `DROP TABLE` 备份中存在的表，新版本添加的表（如 `flow_image`）不会被删除。

恢复后 Liquibase 检测到 `flow_image` 表的创建记录不存在，尝试创建时失败：
```
Table 'flow_image' already exists
```

### 4.2 解决方案

恢复前先 **DROP DATABASE** 再 **CREATE DATABASE**，确保数据库完全清空：

```properties
# 恢复前清空数据库命令
sqlDropCreateCmd=/usr/bin/mysql ... -e "DROP DATABASE IF EXISTS yd_jz; CREATE DATABASE yd_jz;"
```

### 4.3 恢复流程

```
1. 上传备份文件
2. DROP DATABASE IF EXISTS yd_jz; CREATE DATABASE yd_jz;  ← 新增
3. mysql yd_jz < backup.sql
4. 重启后 Liquibase 自动补齐新表/新列
```

### 4.4 代码实现

**BackupService.java：**

```java
@Value("${sqlDropCreateCmd:}")
private String dropCreateCmd;

public void uploadAndRestore(MultipartFile file) {
    // ... 文件校验和保存 ...

    // 先删除并重建数据库
    if (dropCreateCmd != null && !dropCreateCmd.isEmpty()) {
        LogUtils.log_print("清空数据库...");
        String[] dropCmd = buildCommand(dropCreateCmd);
        Process dropProcess = Runtime.getRuntime().exec(dropCmd);
        // ... 错误处理 ...
    }

    // 执行恢复命令
    String[] cmd = buildCommand(restoreCmd + "\"" + filePath + "\"");
    // ...
}
```

### 4.5 兼容性

此方案兼容任何版本的备份文件：
- 旧备份（无 `--databases`）：先清空再恢复，Liquibase 补齐新结构
- 新备份（有 `--databases`）：备份自带 DROP DATABASE，两次删除无影响

## 5. 恢复后自动重启

### 5.1 需求背景

恢复数据库后需要重启服务，让 Liquibase 自动补齐新版本的表结构。手动重启不够便捷。

### 5.2 解决方案

利用 Docker 的 `restart: always` 策略，恢复成功后调用 `System.exit(0)`，Docker 会自动重启容器。

### 5.3 代码实现

```java
// 恢复成功后
LogUtils.log_print("服务将在 3 秒后重启，Liquibase 将自动补齐表结构...");
new Thread(() -> {
    try {
        Thread.sleep(3000);
        log.info("正在重启服务...");
        System.exit(0);  // Docker restart: always 会自动重启
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}).start();
```

### 5.4 完整恢复流程

```
1. 上传备份文件
2. DROP DATABASE → CREATE DATABASE
3. mysql 导入数据
4. 返回成功响应给前端
5. 等待 3 秒
6. System.exit(0)
7. Docker 自动重启
8. Liquibase 补齐表结构
```

## 7. 公告通知系统

### 7.1 需求背景

需要向用户推送公告消息（如版本发布、反馈邀请等），独立于版本更新检查，用户主动获取。

### 7.2 云端 JSON 结构

**notices.json：**
```json
{
  "notices": [
    {
      "id": 1,
      "title": "v2.6.1 发布",
      "content": "新增数据库备份恢复功能",
      "date": "2026-01-26",
      "url": "",
      "expire": "2026-02-28"
    }
  ]
}
```

### 7.3 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | int | 唯一标识，前端记录已读 |
| `title` | string | 公告标题 |
| `content` | string | 公告内容 |
| `date` | string | 发布日期 |
| `url` | string | 跳转链接，空则无 |
| `expire` | string | 过期日期，空则永不过期 |

### 7.4 接口

```
GET /home/getNotices
```

**响应：**
```json
{
  "code": 0,
  "msg": "Success",
  "data": [
    {
      "id": 1,
      "title": "v2.6.1 发布",
      "content": "新增数据库备份恢复功能",
      "date": "2026-01-26",
      "url": "",
      "expire": "2026-02-28"
    }
  ]
}
```

### 7.5 服务端逻辑

- 从云端获取 notices.json
- 自动过滤已过期公告
- 返回未过期公告列表

### 7.6 前端建议

- 本地存储已读 id 列表
- 有未读公告时显示小红点
