## 今日开发内容

### 1. application-local.properties 配置补全

#### 问题描述

后端启动报错：

```
Error creating bean with name 'backupController':
  Unsatisfied dependency expressed through field 'backupService':
Error creating bean with name 'backupService':
  Injection of autowired dependencies failed
...
Caused by: org.springframework.util.PlaceholderResolutionException:
  Could not resolve placeholder 'sqlRestoreCmd' in value "${sqlRestoreCmd}"
```

最外层只说"`backupController` → `backupService` 注入失败"，根因被截在第二层 `Caused by:` —— 是 `BackupService.@Value("${sqlRestoreCmd}")` 没默认值，配置里又缺这个 key，placeholder 解不到 → Spring 上下文起不来。

用户反馈"另一台开发机能起"，说明只是当前这台机器的 `application-local.properties` 是早期版本，没跟上 v2.6.0 / v2.7.0 后追加的 SQL 备份相关 key。

#### 解决方案

对照 `application-local.properties.example` 和当前文件，补全两块：

**A. SQL 备份段（修启动报错）**

```properties
# 操作系统类型：win / ubuntu（本地 win 走 cmd /c，Docker 走 /bin/sh -c）
system.os=win

# 恢复命令
sqlRestoreCmd=mysql -h localhost -P 3306 -uroot -peasy_accounts yd_jz <

# 恢复前清空数据库命令（先删库再建库，确保兼容旧版本备份）
sqlDropCreateCmd=mysql -h localhost -P 3306 -uroot -peasy_accounts -e "DROP DATABASE IF EXISTS yd_jz; CREATE DATABASE yd_jz;"
```

mysql 命令路径与密码沿用现有 `sqldumpCmd` 的风格（不写绝对路径，走 PATH；密码 `easy_accounts`）。

**B. DevTools 禁用 + Hikari 限连**（dev-log 4-23 §9 已决定，这台机器还没同步）

```properties
# 限 Hikari 连接池，避免 DevTools 反复重启累积 sleep 连接耗尽 MySQL max_connections
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.minimum-idle=1

# 禁用 DevTools 自动重启（手动重启更可控；自动重启会导致 [restartedMain] 反复刷连接池）
spring.devtools.restart.enabled=false
spring.devtools.livereload.enabled=false
```

启动日志中 `[restartedMain]` 线程名出现 = DevTools 在自动重启，早晚会触发 `Too many connections`，趁机一起补上。

#### 不动的部分

| 项 | 原因 |
|---|---|
| `version.*` 字段 | CLAUDE.md 红线：发版动作归主管 Claude |
| 数据库 URL / 密码 / 文件路径 | 用户机器特有的环境配置 |
| qwen key / Tomcat 线程优化 / 版本通知 URL 等 example 可选项 | 不引入用户没要的东西 |

#### 验证

启动应可正常起来（`PlaceholderResolutionException` 消失）；后续改代码不再触发自动重启循环，连接池不再累积 sleep 连接。

### 2. 配置项入库可行性分析（讨论，未实现）

#### 背景

v2.7.0 引入了 `app_config` 表（id + domain + config_key + config_value + updated_at，`(domain, config_key)` 唯一），目前仅服务于 `domain=scheduled_flow`（提醒前 N 天 + 提醒时刻）。用户问还有哪些 properties / docker-compose env 可下沉到此表，让最终用户在设置页直接调。

#### 盘点结论

拉取 `docker-compose.yml` 中 server 容器 env（`DB_PASSWORD` / `SQL_BACKUP_TIME` / `ENABLE_LOGIN` / `EXPIRED_TIME` / `SINGLE_LOGIN`）+ 全部 properties，按"是否适合用户在前端设置"分三类：

**🟢 第一阶段（后端独立即可，建议入库）**

| 现配置 | 建议入库位置 | 工程量 |
|---|---|---|
| `auth.expired`（env `EXPIRED_TIME=30`） | `domain=auth, key=token_expired_minutes` | 小：TokenService 改读库 |
| `auth.single_login`（env `SINGLE_LOGIN=true`） | `domain=auth, key=single_login` | 小：登录逻辑读库 |
| `cron.sqlBackupTime`（env `SQL_BACKUP_TIME`） | `domain=backup, key=daily_backup_time`（HH:mm 形式，后端拼 cron） | 中：`@Scheduled(cron=)` 启动期解析，需改 `SchedulingConfigurer` 动态调度 |

接口建议复用 `/scheduledFlow/config/reminder` 既有套路 → 通用 `GET/PUT /system/config/{domain}`，前端按 domain 渲染设置面板。

**🟡 跨端协调（需主管派活）**

- `auth.enable`：运行时切登录开关风险高（已登录用户怎么办？拦截器何时失效？），倾向保持部署期决定
- WebHook SMTP（`SMTP_SERVER/PORT/MAIL/PASSWORD/TO_LIST`）：WebHook 端要改读后端配置
- WebHook `SEND_SQL_BACKUP / SEND_EXCEL`：纯偏好但跨端
- AI `LLM_EASY_ACCOUNTS_API_KEY / URL / MODEL`：跨端，AI 端要改读后端配置

**🔴 必须留 properties / env**

DB 连接 / `server.port` / 循环依赖开关 / Tomcat / 文件路径 / SQL 命令模板 / `system.os` / `webhook_url` / Hikari / Liquibase / 日志 / 版本字段 / 公告 URL —— 启动期解析或部署级常量，运行时改无意义或风险大。

#### 状态

本日为方案讨论，**未动代码**。等用户/主管确认第一阶段启动哪几项再实施。

### 3. 通知消失逻辑产品文案

#### 背景

用户需要给最终用户/帮助文档解释"定时记账提醒什么时候会自动消失"。v2.7.0 §十三 已实现 7 处通知清理触发点，但代码层描述（`advanceCursor` / `invalidateByAccount` / SYS_COMPLETE）不适合直接给用户，需要翻译成产品语言。

#### 输出文案

核心理念：**通知只在还有意义时存在**。一旦预告的事不会再发生或已发生，就自动清掉。

7 种自动消失场景：

| 场景 | 何时消失 |
|---|---|
| 记账成功 | 当天对应的提醒消失 |
| 删除规则 | 该规则全部提醒消失 |
| 修改规则 | 旧提醒可能对不上新计划，全清后按新计划重新生成 |
| 暂停规则 | 暂停期不会执行，全部提醒清空 |
| 规则失效（账户停用 / 分类停用归档） | 规则不能再执行，全部提醒清空 |
| 规则到结束日期 | 规则进入"完成"状态，剩余提醒清空 |
| 错过执行（停机错过） | 系统跳过那天，自动推到下次执行日，并清掉那天的过时提醒 |

一句话版本：

> 提醒会在记账完成、规则删除、修改、暂停、失效、自然结束、或错过执行时自动消失，您不会看到无效的提醒。

## 遇到的坑 / 注意事项

### 1. Spring `@Value` 没默认值会让整个上下文起不来

`@Value("${key}")` 不带默认值时，配置缺该 key → `PlaceholderResolutionException` 直接让 Spring 上下文炸掉，连带链路上所有 bean 注入失败。错误最外层只显示"某 bean 注入失败"，根因要从第二层 `Caused by:` 才能看到 —— 排查时不能只看栈顶，必须贴到第一段 `Caused by:` 的具体异常。

启示：
- 用户必填项就别加默认值（让启动早炸早暴露，比上线后跑一半才发现少配置好）
- 有合理默认值就显式写 `@Value("${key:default}")`，不要依赖外部一定配齐

### 2. application-local.properties 在 .gitignore 中，多机协作会漂移

各台开发机的 `application-local.properties` 是手工维护的，`.example` 模板更新后没人主动同步，容易出现"昨天电脑能起 / 今天换台机器起不来"。

应对：
- 换机器或长时间没用后，先 diff 本地文件 vs `.example`，缺啥补啥
- 补 key 时顺手把 dev-log 里之前决定但本机没落地的本地配置一起补上（如 4-23 §9 的 DevTools / Hikari）

### 3. 部分栈日志容易误导排查方向

最外层栈是 `BackupController` → `BackupService` 注入失败，看起来像备份模块自己有问题。但其实根因是配置缺失，跟备份模块代码毫无关系；甚至跟 v2.7.0 没任何关系。日志要看到 `Caused by:` 才能定位 —— 这一点用户初次排查时容易被误导。
