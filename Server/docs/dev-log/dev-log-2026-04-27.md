### 2. AES 加解密设计（CryptoUtils）

**用户拍板**：项目级简化方案，密钥写死代码 = `easyaccounts`，不走 env。

**实现**：
- 算法 AES-256/CBC/PKCS5Padding
- 密钥派生：`SHA-256("easyaccounts")` → 32 字节
- 每次加密生成 16 字节随机 IV，拼在密文前一起 Base64 入库
- `null` / 空串透传不加密
- 解密失败抛 `BusinessException(CRYPTO_FAILED)`，邮件流程整体失败，不发降级邮件

**为啥不直接用 `"easyaccounts"` 当密钥**：12 字节不符合 AES-128/192/256 任何长度要求，必须先派生。SHA-256 派生比"补零凑长度"安全得多。

**测试覆盖**：10 个用例（往返 / null / 空串 / 特殊字符 / IV 随机性 / 错密钥 / 短密文 / 非法 Base64）。

### 3. 备份调度热生效（最有意思的一段）

**改造前**：`@Scheduled(cron = "${cron.sqlBackupTime}")` 启动期解析，改 cron 必须重启容器。

**改造后**：
- `@PostConstruct` 时 `taskScheduler.schedule(this::doBackup, new CronTrigger(cron))`
- 用 `ApplicationEventPublisher` 把 `BackupConfigService` 与 `SQLBackUpTask` 解耦
- `BackupConfigService.update()` → `publishEvent(BackupConfigChangedEvent)` → `SQLBackUpTask.@EventListener` → `cancel(false)` 旧 future + 重新 schedule
- 新 cron **下一次计算时立刻生效**，不需要重启

**实测验证**（日志）：
```
[http-nio-8083-exec-1] INFO  SQLBackUpTask - backup config changed, rescheduling...
[http-nio-8083-exec-1] INFO  SQLBackUpTask - 自动备份已安排：cron=0 0 22 * * ?
```

**为什么 `cancel(false)` 不用 `cancel(true)`**：备份正在执行（mysqldump 中）时，`true` 会打断线程留下半截 .sql 文件。`false` 让正在跑的备份完成，但跑完不会再被调度。

### 4. 邮件统一发送服务（MailService）

**初版方案**：6 个语义化方法，每个方法各自字符串拼接 + 各自检查全局开关。

**用户反馈**："这也是字符串拼接，重复劳动"。

**重构后**：
- 抽象 `MailEnvelope`（subject / summary / fields Map / advice / attachment / category）
- 每个公共方法只填 envelope，4-7 行业务代码
- 唯一私有 `send(MailEnvelope env)` 处理所有公共逻辑：`[EasyAccounts]` 前缀、字段块格式、签名、全局开关检查（按 `Category` enum 分发）、SMTP 连接、错误处理
- 加新邮件类型 = 新增 1 个 enum 值 + 1 个公共方法 + 0 个新模板

**SMTP 协议适配**：端口 465 自动走 SMTPS（隐式 SSL），其他端口走 STARTTLS。**这一处修复了旧 WebHook Python 实现的 bug**——它一刀切 STARTTLS，QQ 邮箱默认 465 端口 + STARTTLS 实际跑不通。

**实测**（用户的 QQ 邮箱配置）：
```
配 SMTP → POST /system/config/mail/test
→ {"success":true,"message":"邮件已发送到：xxx@qq.com,xxx@outlook.com"}
→ 双收件人邮箱实际收到测试邮件
```

## 遇到的坑 / 注意事项

### 1. Liquibase changeset 在未发布版本可以重写

最初我做 Phase 1 时，按生产实践拆了两个 changeset（老的 `2.7.0-seed-app-config-scheduled-flow-reminder` 不动，新加 `2.7.0-seed-app-config-mail-backup-auth`）。用户问"为什么两个？"我解释了 Liquibase 校验和机制。用户回："2.7.0 还没上线，DB 随便改"。

**反思**：未发布版本期间，Liquibase changeset 可以直接改写、合并、删除，不必拘泥于"已执行 changeset 不能动"的生产规则。已记录到 memory/feedback_pre_release_changeset_fluid.md。

后来合成单一 `2.7.0-seed-app-config` changeset 含 17 行 INSERT IGNORE，更干净。

### 2. WebHook 旧 Python 实现实际是个无效 hack

整理时发现旧设计三处明显问题：
- `NotificationWebHook` 把通知正文字节假装成"文件"用 multipart 上传，WebHook 端 decode UTF-8 还原 —— hack
- `SEND_SQL_BACKUP=False` env 开关**实际从未生效**（Java 传 `"sql"`，Python 检查 `"sql_backup"`，永远不匹配）
- 端口 465 一刀切 STARTTLS，QQ 邮箱默认 465 SMTPS 模式实际跑不通

新 MailService 全部修正。

### 3. `/home/getVersion` 接口字段精简

删 `versions.webhookBranch` 字段，前端如果还在读会拿到 undefined。**前端 Claude 必须同步处理**。已在 Phase 8 跨端清单标记。

### 4. 拦截器始终注册的性能担忧

每个请求多一次 `AuthConfigService.isLoginEnable()` DB 读取。担心性能但**没加 cache**——本地 SQLite-style 单连接 MySQL 读延迟 < 1ms，单用户场景压根不是瓶颈。如果未来真需要，可以加 30s Caffeine 短缓存。

### 5. application-local.properties 跨机漂移

不同开发机的本地配置漂移问题不是首次踩。这次清理 8 个 env 时，发现本机和 example 默认值不完全对齐（如 `auth.expired` 一个 30 一个 90）。建议团队约定：每次特性合并前 diff 一下 example 文件，把 example 当 source of truth。
