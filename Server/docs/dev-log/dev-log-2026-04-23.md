### 1. 数据库 4 张新表

#### 1.1 需求背景

产品需求（`docs/v2.7.0/plan-scheduled-flow.md`）明确"定时记账与快记模板独立共存，不互转"，**不能复用 `flow_template`**，必须新建独立的规则表 + 执行日志表。事前提醒需要本地可读写的通知表（不能复用云端公告 `NoticeService`）。全局"提醒前 N 天 / 提醒时刻"两个字段需要一个配置表。

### 2. 周期计算器 CycleCalculator

#### 2.1 设计目标

独立纯函数工具类，**无 Spring 依赖**，好写单测。所有比较用 `LocalDate` 整体比（不允许拆 `getDayOfMonth()` 比较）。

#### 2.2 对外接口

```java
// 算下一个执行日：严格大于 from 的最近一天
LocalDate nextRunDate(int cycleType, String cycleDatesJson, LocalDate from)

// 预览下一轮执行日：每月=下月 / 每年=下年 / 每日每周=空
List<LocalDate> previewNextCycle(int cycleType, String cycleDatesJson, LocalDate anchor)
```

#### 2.3 月末回退的关键写法

```java
// 为"号数 d"构造完整 LocalDate，自动月末回退
int maxDay = ym.lengthOfMonth();
ym.atDay(Math.min(d, maxDay));
```

- 每月 31 号遇 2 月 → 28/29；遇 4/6/9/11 → 30
- 每年 2-30 无效日期 → 2 月末
- 每年 4-31 无效 → 4-30

#### 2.4 用户提的坑：月初 vs 上月月末

用户明确提醒："用 Date/LocalDate 包装，月初比上月月末大"。

**反例**（只比号数）：`5/30 vs 6/1`，号数 `1 < 30`，错判"下月 1 号还没到"。

**正例**（LocalDate 整体比）：`6/1.isAfter(5/30)` → true，正确。

整个 CycleCalculator 全程 LocalDate，Service 在边界做 `Date ↔ LocalDate` 转换：

```java
private static LocalDate toLocalDate(Date date) {
    return date.toInstant().atZone(ZoneId.systemDefault()).toLocalDate();
}
private static Date toDate(LocalDate localDate) {
    return Date.from(localDate.atStartOfDay(ZoneId.systemDefault()).toInstant());
}
```

#### 2.5 单测覆盖（23 个）

- 每日跨月
- 每周跨年（12/31 周四 → 下一个周二 = 1/5）
- 每月核心：`from=5/30, [5,20]` → `6/5`
- 每月 31 号回退 2/28、2/29（闰年 2028）、4/30
- 每年 2/29 平年回退 2/28
- 每年 2/30 闰年回退 2/29、平年回退 2/28
- 每年 4/31 回退 4/30
- 预览下月/下年
- 每日/每周预览返回空
- 非法 cycleType / 空 cycleDates 抛 `IllegalArgumentException`

### 3. 状态机 ScheduledFlowRuleStateMachine

#### 3.1 守门员模式

规则 5 种状态，改状态的业务路径散布在 Service / 扫描器 / 事件挂钩 / 启动补偿多处。**禁止到处散落的 `rule.setStatus(x)`**，集中一处用状态机统一守门。

#### 3.2 5 态 5 事件转移矩阵

| 源 \ 目标 | 开始 | 暂停 | 完成 | 失效 |
|---|---|---|---|---|
| 未开始 | sys（到 start_date）| — | — | — |
| 开始 | — | user(pause) | sys（到 end_date） | sys/主数据事件 |
| 暂停 | user(start) | — | — | — |
| 完成 | user(start) | — | — | — |
| 失效 | user(start) | — | — | — |

其他组合一律抛 `BusinessException(ILLEGAL_STATE_TRANSITION)`。

#### 3.3 实现结构

```java
public static void transit(ScheduledFlowRule rule, Event event) {
    int from = rule.getStatus();
    int to = calcTarget(from, event);  // 非法会抛异常
    rule.setStatus(to);                 // 合法才改
}
```

`calcTarget` 里对每个事件 switch + if 检查源状态，非法 break 到最后统一 throw。

#### 3.4 关于 `dirty` 字段的放弃

初版设计在 `scheduled_flow_rule` 表加了 `dirty` 布尔字段 + R7 Review 点，用于实现产品"从非执行态回到开始必须先编辑过"的约束。

**用户澄清**：

> 完成后规则不能启动，想启动必须改开始日期；失效状态必须补齐失效字段；暂停想恢复本身就是用户按的。都需要用户手动编辑，这个字段没有意义。

放弃 `dirty` 字段：Entity/yaml/feature-guide/状态机全部清理。

start 接口的保护机制改成**字段合法性校验**：

- `next_run_date` 能算出来且 ≤ `end_date`
- 引用的账户未停用、分类未停用/归档

用户什么都不改就从"完成"状态点开始，第一步就会因为 `next_run_date > end_date` 被拦下。自然机制代替人为标记位。

#### 3.5 单测（21 个）

- 7 个合法转移：每个事件 × 每个合法前置
- 12 个非法转移：覆盖所有错误组合
- 1 个错误码断言：非法抛 `ILLEGAL_STATE_TRANSITION`
- 1 个副作用安全：非法时 `rule.status` 不被改动

private void validateMasterDataUsable(ScheduledFlowRule rule) {

### 5. 执行扫描器 ScheduledFlowExecuteTask

#### 5.1 调度入口

参考现有 `SQLBackUpTask` 的风格：

```java
@Configuration
@EnableScheduling
public class ScheduledFlowExecuteTask {
    @Scheduled(cron = "0 * * * * ?")  // 每分钟第 0 秒
    public void scan() { ... }
}
```

#### 5.2 两步扫描

**步骤 1**：NOT_START 规则到 start_date → 自动切 RUNNING

```java
List<rule> starting = ruleRepo.findDueRules(NOT_START, today);
for each: ruleService.markRunning(r);
```

**步骤 2**：RUNNING 规则按四分支决策

```
┌── last_run_date == today         → skip（今天执行过）
├── next_run_date < today           → 只推游标（历史遗留）
├── now < run_time                  → skip（没到点）
├── 当前分钟 == run_time 的分钟     → 执行 + 写日志 + 推游标
└── now > run_time（分钟过了）      → 只推游标（今天错过）
```

#### 5.3 核心原则：**任何扫描命中，游标要么不动要么前进，绝不卡住**

用户提出的 corner case：`next_run_date` 卡在过去，日期就被永久错过。

初版设计有漏洞：扫到"分钟不对"直接 skip，游标不变。

修正后四分支明确：**"错过"和"没到"是两件事**——没到等、错过推。

```
Before:  if (分钟不对) skip;                          ← 漏掉"已过"要推
After:   if (next < today) advance(不执行);           ← 历史遗留
         if (now < run_time) skip;                    ← 没到，等
         if (分钟对上) execute + advance;
         else advance(不执行);                        ← 已过，推
```

#### 5.4 失败分类

```java
try {
    ruleService.executeRuleOrThrow(rule, today);
} catch (BusinessException be) {
    if (isMasterDataError(be.getCode())) {
        // 账户停用 / 分类停用或归档 / 分类有子分类 / 主数据不存在
        → recordFailure(category=1) + markInvalid(rule)
    } else {
        → recordFailure(category=2) + advanceCursor
    }
} catch (Exception e) {
    → recordFailure(category=2) + advanceCursor
}
```

产品原则：**任何失败不重试、不补记**。

#### 7.2 ReminderDispatchTask 逻辑

```java
@Scheduled(cron = "0 * * * * ?")
public void scan() {
    // 只在全局提醒时刻那分钟工作
    if (now != remind_time) return;

    int N = appConfigService.getRemindBeforeDays();
    LocalDate targetDate = today + N;

    List<rule> rules = ruleRepo.findRulesForReminder(RUNNING, targetDate);
    for rule:
        if (noticeService.existsReminderFor(rule.id, targetDate)) continue;
        noticeService.create(type=1, title, content, rule.id, targetDate);
        if (rule.emailEnabled) notificationWebHook.sendEmail(title, content);
}
```

#### 7.3 执行扫描与提醒扫描共用游标

同一个 `next_run_date` 字段，两个扫描器从不同时间角度看它：

- **执行扫描**：`next_run_date <= today`（今天要记账）
- **提醒扫描**：`next_run_date = today + N`（N 天后要记账，提前告诉你）

#### 7.4 执行后自动删提醒（产品 §7.5 后补需求）

`executeRuleOrThrow` 成功生成 flow 后：

```java
noticeRepo.deleteByRelatedRuleIdAndRelatedRunDate(rule.getId(), toDate(today));
```

执行完就把对应那条"N 天后要记账"的提醒清掉，避免用户看到过期提醒。

#### 7.5 邮件 WebHook 薄层

现有 `FileMakeWebHook` 是发文件的，不适合纯通知。新建 `NotificationWebHook`：

```java
public void sendEmail(String subject, String body) {
    Map payload = {type:"email", subject, body};
    POST webhook_url application/json payload;
    // 失败记 warn，不抛异常（邮件失败不影响站内通知）
}
```

WebHook 端对接 payload 结构需要 WebHook Claude 同步。

### 9. 本地开发环境调整

#### 9.1 问题：MySQL `Too many connections`

数据库恢复时报 `ERROR 1040 (HY000): Too many connections`。

**原因**：Spring DevTools 热重载每次创建新 Hikari 连接池，旧的未完全释放。反复改代码后累积几十个 sleep 连接，超过 MySQL 默认 `max_connections=151`。

#### 9.2 解决方案

本地 `application-local.properties` 追加：

```properties
# 禁用 devtools 自动重启，偏好手动重启
spring.devtools.restart.enabled=false
spring.devtools.livereload.enabled=false

# 限 Hikari 连接池，避免本地累积耗尽 MySQL 连接数
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.minimum-idle=1
```

改完必须重启一次让配置生效，之后改代码**不再自动重启**，全部手动停+启。

### 10. dirty 字段的设计来回

#### 10.1 初版设计（被推翻）

为了实现产品"从非执行态回到开始必须先编辑过"的要求，Entity + yaml 加了 `dirty` 布尔字段，PUT 修改置 1，start 成功置 0。

#### 10.2 用户澄清

> 完成状态想启动必须改开始日期；失效状态必须补齐字段；暂停想恢复本身就是用户按的。都需要用户手动编辑，dirty 字段没意义。

#### 10.3 收敛后的设计

后端不维护 UX 层面的"已编辑"标记。start 接口做**字段合法性校验**：

- `next_run_date` 能算出来且 ≤ `end_date`
- 账户未停用 / 分类未停用或归档

用户什么都不改从完成状态点开始 → 自然被 `RULE_EXPIRED` 拦下。

"编辑 + 点开始"属于前端 UX 约束，后端只关心状态合法转移 + 字段合法性。

#### 10.4 后续清理

- yaml 删 dirty 列
- Entity 删 dirty 字段
- feature-guide §1.2 / §2.1 / §3 状态机图 / §八 Review 点 R7 全部同步清理
- 状态机转移矩阵简化（`USER_START` 不再带 dirty 前置条件）

## 技术要点

### 1. 游标前进原则（不卡死）

任何扫描命中规则，**要么前进、要么不动（等或已完成），绝不停留在过去**。事务提交即状态变更；失败回滚相当于"没发生过"，下次扫描重来。

| 场景 | 游标 | 执行 | 日志 |
|---|---|---|---|
| 今天已执行 | 不动 | ❌ | — |
| next<today（历史遗留） | 前进 | ❌ | — |
| 没到点 | 不动（等） | ❌ | — |
| 正好到点 | 前进 | ✅ | 成功 |
| 已过点 | 前进 | ❌ | — |
| 主数据失败 | 不再前进（置失效） | ❌ | 失败-主数据 |
| 其他失败 | 前进 | ❌ | 失败-其他 |

### 2. Date ↔ LocalDate 边界转换

| 层 | 日期表达 |
|---|---|
| JPA Entity | `java.util.Date` + `@Temporal(DATE)` |
| Service 业务逻辑 | `LocalDate` |
| CycleCalculator | `LocalDate`（全程） |
| REST DTO | `String` (yyyy-MM-dd) |

Service 是转换枢纽，CycleCalculator 永远不见 `Date`。

### 3. JSON 字符串存 cycle_dates 的权衡

| 方案 | 优点 | 缺点 |
|---|---|---|
| ✅ JSON 字符串 | 不拉关联表，表结构简单；多选天然表达 | SQL 层无法索引具体日期 |
| ❌ 关联表 | SQL 可索引；规范化 | 表数量 +1；读写多一次 JOIN |

本项目周期日期只在规则详情/编辑时读写，不需要按具体日期索引查询，JSON 方案够用。

### 4. 循环依赖的取舍

`AccountService ↔ ScheduledFlowRuleService ↔ FlowService` 字段注入循环靠 `spring.main.allow-circular-references=true` 兜底。

| 方案 | 优点 | 缺点 |
|---|---|---|
| ✅ 直调（当前） | 代码直观，调用链清晰 | 字段注入循环，依赖 allow-circular |
| 👀 ApplicationEvent | 解耦彻底 | 流程追踪困难，本项目规模不值得 |

本版本接受直调，长期若 Service 间关系变复杂再重构。

### 5. "扫描器 + 游标"的调度模式

没有为每条规则起一个定时器，而是**一个全局扫描器每分钟醒来读数据库游标**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| ✅ 全局扫描 + 游标 | 服务重启自动恢复；规则增删改无需重配置定时器 | HH:mm 精度延迟最多 1 分钟 |
| ❌ 每规则一定时器 | 精度高 | 生命周期管理复杂，重启要重建所有定时器 |

产品精度要求 HH:mm（分钟级），扫描方案够用。参考 `SQLBackUpTask` 的 `@Scheduled + cron` 风格。
