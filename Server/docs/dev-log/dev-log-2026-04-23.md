### 1. 数据库 4 张新表

#### 1.1 需求背景

产品需求（`docs/v2.7.0/plan-scheduled-flow.md`）明确"定时记账与快记模板独立共存，不互转"，**不能复用 `flow_template`**，必须新建独立的规则表 + 执行日志表。事前提醒需要本地可读写的通知表（不能复用云端公告 `NoticeService`）。全局"提醒前 N 天 / 提醒时刻"两个字段需要一个配置表。

### 2. 周期计算器 CycleCalculator

#### 2.1 设计目标

独立纯函数工具类，**无 Spring 依赖**，好写单测。所有比较用 `LocalDate` 整体比（不允许拆 `getDayOfMonth()` 比较）。

#### 2.2 对外接口

```java
// 算下一个执行日：严格大于 from 的最近一天
LocalDate nextRunDate(int cycleType, String cycleDatesJson, LocalDate from)

// 预览下一轮执行日：每月=下月 / 每年=下年 / 每日每周=空
List<LocalDate> previewNextCycle(int cycleType, String cycleDatesJson, LocalDate anchor)
```

#### 2.3 月末回退的关键写法

```java
// 为"号数 d"构造完整 LocalDate，自动月末回退
int maxDay = ym.lengthOfMonth();
ym.atDay(Math.min(d, maxDay));
```

- 每月 31 号遇 2 月 → 28/29；遇 4/6/9/11 → 30
- 每年 2-30 无效日期 → 2 月末
- 每年 4-31 无效 → 4-30

#### 2.4 用户提的坑：月初 vs 上月月末

用户明确提醒："用 Date/LocalDate 包装，月初比上月月末大"。

**反例**（只比号数）：`5/30 vs 6/1`，号数 `1 < 30`，错判"下月 1 号还没到"。

**正例**（LocalDate 整体比）：`6/1.isAfter(5/30)` → true，正确。

整个 CycleCalculator 全程 LocalDate，Service 在边界做 `Date ↔ LocalDate` 转换：

```java
private static LocalDate toLocalDate(Date date) {
    return date.toInstant().atZone(ZoneId.systemDefault()).toLocalDate();
}
private static Date toDate(LocalDate localDate) {
    return Date.from(localDate.atStartOfDay(ZoneId.systemDefault()).toInstant());
}
```

#### 2.5 单测覆盖（23 个）

- 每日跨月
- 每周跨年（12/31 周四 → 下一个周二 = 1/5）
- 每月核心：`from=5/30, [5,20]` → `6/5`
- 每月 31 号回退 2/28、2/29（闰年 2028）、4/30
- 每年 2/29 平年回退 2/28
- 每年 2/30 闰年回退 2/29、平年回退 2/28
- 每年 4/31 回退 4/30
- 预览下月/下年
- 每日/每周预览返回空
- 非法 cycleType / 空 cycleDates 抛 `IllegalArgumentException`

### 3. 状态机 ScheduledFlowRuleStateMachine

#### 3.1 守门员模式

规则 5 种状态，改状态的业务路径散布在 Service / 扫描器 / 事件挂钩 / 启动补偿多处。**禁止到处散落的 `rule.setStatus(x)`**，集中一处用状态机统一守门。

#### 3.2 5 态 5 事件转移矩阵

| 源 \ 目标 | 开始 | 暂停 | 完成 | 失效 |
|---|---|---|---|---|
| 未开始 | sys（到 start_date）| — | — | — |
| 开始 | — | user(pause) | sys（到 end_date） | sys/主数据事件 |
| 暂停 | user(start) | — | — | — |
| 完成 | user(start) | — | — | — |
| 失效 | user(start) | — | — | — |

其他组合一律抛 `BusinessException(ILLEGAL_STATE_TRANSITION)`。

#### 3.3 实现结构

```java
public static void transit(ScheduledFlowRule rule, Event event) {
    int from = rule.getStatus();
    int to = calcTarget(from, event);  // 非法会抛异常
    rule.setStatus(to);                 // 合法才改
}
```

`calcTarget` 里对每个事件 switch + if 检查源状态，非法 break 到最后统一 throw。

#### 3.4 关于 `dirty` 字段的放弃

初版设计在 `scheduled_flow_rule` 表加了 `dirty` 布尔字段 + R7 Review 点，用于实现产品"从非执行态回到开始必须先编辑过"的约束。

**用户澄清**：

> 完成后规则不能启动，想启动必须改开始日期；失效状态必须补齐失效字段；暂停想恢复本身就是用户按的。都需要用户手动编辑，这个字段没有意义。

放弃 `dirty` 字段：Entity/yaml/feature-guide/状态机全部清理。

start 接口的保护机制改成**字段合法性校验**：

- `next_run_date` 能算出来且 ≤ `end_date`
- 引用的账户未停用、分类未停用/归档

用户什么都不改就从"完成"状态点开始，第一步就会因为 `next_run_date > end_date` 被拦下。自然机制代替人为标记位。

#### 3.5 单测（21 个）

- 7 个合法转移：每个事件 × 每个合法前置
- 12 个非法转移：覆盖所有错误组合
- 1 个错误码断言：非法抛 `ILLEGAL_STATE_TRANSITION`
- 1 个副作用安全：非法时 `rule.status` 不被改动

private void validateMasterDataUsable(ScheduledFlowRule rule) {

### 5. 执行扫描器 ScheduledFlowExecuteTask

#### 5.1 调度入口

参考现有 `SQLBackUpTask` 的风格：

```java
@Configuration
@EnableScheduling
public class ScheduledFlowExecuteTask {
    @Scheduled(cron = "0 * * * * ?")  // 每分钟第 0 秒
    public void scan() { ... }
}
```

#### 5.2 两步扫描

**步骤 1**：NOT_START 规则到 start_date → 自动切 RUNNING

```java
List<rule> starting = ruleRepo.findDueRules(NOT_START, today);
for each: ruleService.markRunning(r);
```

**步骤 2**：RUNNING 规则按四分支决策

```
┌── last_run_date == today         → skip（今天执行过）
├── next_run_date < today           → 只推游标（历史遗留）
├── now < run_time                  → skip（没到点）
├── 当前分钟 == run_time 的分钟     → 执行 + 写日志 + 推游标
└── now > run_time（分钟过了）      → 只推游标（今天错过）
```

#### 5.3 核心原则：**任何扫描命中，游标要么不动要么前进，绝不卡住**

用户提出的 corner case：`next_run_date` 卡在过去，日期就被永久错过。

初版设计有漏洞：扫到"分钟不对"直接 skip，游标不变。

修正后四分支明确：**"错过"和"没到"是两件事**——没到等、错过推。

```
Before:  if (分钟不对) skip;                          ← 漏掉"已过"要推
After:   if (next < today) advance(不执行);           ← 历史遗留
         if (now < run_time) skip;                    ← 没到，等
         if (分钟对上) execute + advance;
         else advance(不执行);                        ← 已过，推
```

#### 5.4 失败分类

```java
try {
    ruleService.executeRuleOrThrow(rule, today);
} catch (BusinessException be) {
    if (isMasterDataError(be.getCode())) {
        // 账户停用 / 分类停用或归档 / 分类有子分类 / 主数据不存在
        → recordFailure(category=1) + markInvalid(rule)
    } else {
        → recordFailure(category=2) + advanceCursor
    }
} catch (Exception e) {
    → recordFailure(category=2) + advanceCursor
}
```

产品原则：**任何失败不重试、不补记**。

#### 7.2 ReminderDispatchTask 逻辑

```java
@Scheduled(cron = "0 * * * * ?")
public void scan() {
    // 只在全局提醒时刻那分钟工作
    if (now != remind_time) return;

    int N = appConfigService.getRemindBeforeDays();
    LocalDate targetDate = today + N;

    List<rule> rules = ruleRepo.findRulesForReminder(RUNNING, targetDate);
    for rule:
        if (noticeService.existsReminderFor(rule.id, targetDate)) continue;
        noticeService.create(type=1, title, content, rule.id, targetDate);
        if (rule.emailEnabled) notificationWebHook.sendEmail(title, content);
}
```

#### 7.3 执行扫描与提醒扫描共用游标

同一个 `next_run_date` 字段，两个扫描器从不同时间角度看它：

- **执行扫描**：`next_run_date <= today`（今天要记账）
- **提醒扫描**：`next_run_date = today + N`（N 天后要记账，提前告诉你）

#### 7.4 执行后自动删提醒（产品 §7.5 后补需求）

`executeRuleOrThrow` 成功生成 flow 后：

```java
noticeRepo.deleteByRelatedRuleIdAndRelatedRunDate(rule.getId(), toDate(today));
```

执行完就把对应那条"N 天后要记账"的提醒清掉，避免用户看到过期提醒。

#### 7.5 邮件 WebHook 薄层

现有 `FileMakeWebHook` 是发文件的，不适合纯通知。新建 `NotificationWebHook`：

```java
public void sendEmail(String subject, String body) {
    Map payload = {type:"email", subject, body};
    POST webhook_url application/json payload;
    // 失败记 warn，不抛异常（邮件失败不影响站内通知）
}
```

WebHook 端对接 payload 结构需要 WebHook Claude 同步。

### 9. 本地开发环境调整

#### 9.1 问题：MySQL `Too many connections`

数据库恢复时报 `ERROR 1040 (HY000): Too many connections`。

**原因**：Spring DevTools 热重载每次创建新 Hikari 连接池，旧的未完全释放。反复改代码后累积几十个 sleep 连接，超过 MySQL 默认 `max_connections=151`。

#### 9.2 解决方案

本地 `application-local.properties` 追加：

```properties
# 禁用 devtools 自动重启，偏好手动重启
spring.devtools.restart.enabled=false
spring.devtools.livereload.enabled=false

# 限 Hikari 连接池，避免本地累积耗尽 MySQL 连接数
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.minimum-idle=1
```

改完必须重启一次让配置生效，之后改代码**不再自动重启**，全部手动停+启。

### 10. dirty 字段的设计来回

#### 10.1 初版设计（被推翻）

为了实现产品"从非执行态回到开始必须先编辑过"的要求，Entity + yaml 加了 `dirty` 布尔字段，PUT 修改置 1，start 成功置 0。

#### 10.2 用户澄清

> 完成状态想启动必须改开始日期；失效状态必须补齐字段；暂停想恢复本身就是用户按的。都需要用户手动编辑，dirty 字段没意义。

#### 10.3 收敛后的设计

后端不维护 UX 层面的"已编辑"标记。start 接口做**字段合法性校验**：

- `next_run_date` 能算出来且 ≤ `end_date`
- 账户未停用 / 分类未停用或归档

用户什么都不改从完成状态点开始 → 自然被 `RULE_EXPIRED` 拦下。

"编辑 + 点开始"属于前端 UX 约束，后端只关心状态合法转移 + 字段合法性。

#### 10.4 后续清理

- yaml 删 dirty 列
- Entity 删 dirty 字段
- feature-guide §1.2 / §2.1 / §3 状态机图 / §八 Review 点 R7 全部同步清理
- 状态机转移矩阵简化（`USER_START` 不再带 dirty 前置条件）

## 技术要点

### 1. 游标前进原则（不卡死）

任何扫描命中规则，**要么前进、要么不动（等或已完成），绝不停留在过去**。事务提交即状态变更；失败回滚相当于"没发生过"，下次扫描重来。

| 场景 | 游标 | 执行 | 日志 |
|---|---|---|---|
| 今天已执行 | 不动 | ❌ | — |
| next<today（历史遗留） | 前进 | ❌ | — |
| 没到点 | 不动（等） | ❌ | — |
| 正好到点 | 前进 | ✅ | 成功 |
| 已过点 | 前进 | ❌ | — |
| 主数据失败 | 不再前进（置失效） | ❌ | 失败-主数据 |
| 其他失败 | 前进 | ❌ | 失败-其他 |

### 2. Date ↔ LocalDate 边界转换

| 层 | 日期表达 |
|---|---|
| JPA Entity | `java.util.Date` + `@Temporal(DATE)` |
| Service 业务逻辑 | `LocalDate` |
| CycleCalculator | `LocalDate`（全程） |
| REST DTO | `String` (yyyy-MM-dd) |

Service 是转换枢纽，CycleCalculator 永远不见 `Date`。

### 3. JSON 字符串存 cycle_dates 的权衡

| 方案 | 优点 | 缺点 |
|---|---|---|
| ✅ JSON 字符串 | 不拉关联表，表结构简单；多选天然表达 | SQL 层无法索引具体日期 |
| ❌ 关联表 | SQL 可索引；规范化 | 表数量 +1；读写多一次 JOIN |

本项目周期日期只在规则详情/编辑时读写，不需要按具体日期索引查询，JSON 方案够用。

### 4. 循环依赖的取舍

`AccountService ↔ ScheduledFlowRuleService ↔ FlowService` 字段注入循环靠 `spring.main.allow-circular-references=true` 兜底。

| 方案 | 优点 | 缺点 |
|---|---|---|
| ✅ 直调（当前） | 代码直观，调用链清晰 | 字段注入循环，依赖 allow-circular |
| 👀 ApplicationEvent | 解耦彻底 | 流程追踪困难，本项目规模不值得 |

本版本接受直调，长期若 Service 间关系变复杂再重构。

### 5. "扫描器 + 游标"的调度模式

没有为每条规则起一个定时器，而是**一个全局扫描器每分钟醒来读数据库游标**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| ✅ 全局扫描 + 游标 | 服务重启自动恢复；规则增删改无需重配置定时器 | HH:mm 精度延迟最多 1 分钟 |
| ❌ 每规则一定时器 | 精度高 | 生命周期管理复杂，重启要重建所有定时器 |

产品精度要求 HH:mm（分钟级），扫描方案够用。参考 `SQLBackUpTask` 的 `@Scheduled + cron` 风格。

## 十一、自测回归：5 个 bug 的定位与修复

P2/P3/P4/P5 代码落盘后做端到端自测（curl 打接口 + 观察扫描器 + 对照数据库），陆续发现并修掉 5 个问题。

### 11.1 Bug #1 · `java.sql.Date.toInstant()` 抛 UnsupportedOperationException

**现象**
```
scheduling-1 ERROR ScheduledFlowExecuteTask - scan error on rule 1: null
java.lang.UnsupportedOperationException
    at java.sql.Date.toInstant(Date.java:316)
    at ScheduledFlowExecuteTask.toLocalDate(:169)
```

**根因**

Hibernate 从 `@Temporal(TemporalType.DATE)` 列读出的实际类型是 `java.sql.Date`（继承自 `java.util.Date`），**它重写了 `toInstant()` 强制抛 `UnsupportedOperationException`**。扫描器和 Service 里的 `toLocalDate` 直接用 `date.toInstant()` 就炸了。

**修复**

两处 `toLocalDate`（Task + Service）都改用 `getTime()` 绕过：

```java
private static LocalDate toLocalDate(Date date) {
    if (date == null) return null;
    // 兼容 java.sql.Date：它重写的 toInstant() 抛 UnsupportedOperationException
    return new java.sql.Date(date.getTime()).toLocalDate();
}
```

### 11.2 Bug #2 · update/start 时每日周期"跳过今天"

**现象**

PUT 更新规则（startDate=今天，每日）→ 返回的 `nextRunDate=明天`，应该是今天。

**根因**

`baselineForRecompute` 当 `startDate <= today` 时 `from=today`，CycleCalculator 每日分支返回 `from + 1 day = 明天`。导致规则"永远落后今天一天"。

**修复**

```java
// 旧
return startDate.isAfter(today) ? startDate.minusDays(1) : today;

// 新：max(today, startDate) - 1
LocalDate base = startDate.isAfter(today) ? startDate : today;
return base.minusDays(1);
```

语义：让 "严格大于 from" 的 next 能**落回**基准当天。

### 11.3 Bug #3 · 失效挂钩只覆盖 RUNNING 规则

**现象**

建一条 `NOT_START` 规则引用账户 X → 停用账户 X → 规则状态不变、accountId 仍指向已停用账户。

**根因**

`ScheduledFlowRuleService.invalidateByAccount/Type` 内部查询写死 `status = RUNNING`。NOT_START、PAUSED、COMPLETED 状态的规则引用的账户/分类停用时根本不被查出来。

**修复 3 处**：

1. Repository 查询去掉 status 过滤（INVALID 规则的 accountId/typeId 已经为 null，天然不会再被查到）：

```java
@Query("SELECT r FROM ScheduledFlowRule r " +
       "WHERE r.accountId = :accountId OR r.accountToId = :accountId")
List<ScheduledFlowRule> findRulesByAccountId(Integer accountId);
```

2. Service 方法改用新查询：
```java
List<ScheduledFlowRule> rules = ruleRepo.findRulesByAccountId(accountId);
```

3. 状态机 `SYS_INVALIDATE` 放宽前置 —— 从"仅 RUNNING"改为"非 INVALID 均可"：
```java
case SYS_INVALIDATE:
    if (from != ScheduledFlowConst.STATUS_INVALID) {
        return ScheduledFlowConst.STATUS_INVALID;
    }
    break;
```

**副作用**：状态机单测里 `sysInvalidate_fromNotStart_throws` / `sysInvalidate_fromPaused_throws` 行为反转，需要单测同步更新（后续待办）。

### 11.4 Bug #4 · 提醒扫描漏掉 NOT_START 规则

**现象**

新建规则 `startDate=明天, reminderEnabled=true`，设提醒时间到 1 分钟后，等了一分钟但 `user_notice` 表没数据。

**根因**

`findRulesForReminder` 查询写死 `status = RUNNING`。但规则创建后到 startDate 之前都是 NOT_START 状态 —— 提醒扫描这个阶段把它漏了。

**修复**

Repository 改成 `status IN :statuses`，Task 传入 `[NOT_START, RUNNING]`：

```java
@Query("SELECT r FROM ScheduledFlowRule r " +
       "WHERE r.status IN :statuses AND r.reminderEnabled = true " +
       "AND r.nextRunDate >= :lower AND r.nextRunDate <= :upper")
List<ScheduledFlowRule> findRulesForReminder(List<Integer> statuses, Date lower, Date upper);
```

产品语义：只有 PAUSED / COMPLETED / INVALID 不该被提醒。

### 11.5 Bug #5 · 提醒窗口边界场景：规则 1 天后执行 + 3 天前提醒 → 无通知

**现象**

设 `remindBeforeDays=3`，建规则 `startDate=明天`（next_run_date=明天）。按旧逻辑提醒扫描找 `next_run_date = today+3` 的规则 —— **严格等于**，规则的 next=明天（today+1）永远不命中。用户永远收不到提醒。

**根因**

旧查询条件 `next_run_date = today + N` 是**单点匹配**。当规则的提醒窗口已经开启（`next < today+N`）时落在窗口内部，单点查询无法触达。

**修复（两头夹）**：

1. **查询改区间** `next_run_date ∈ [today, today+N]`：
```java
@Query("... AND r.nextRunDate >= :lower AND r.nextRunDate <= :upper")
```

2. **新增 `ReminderService.checkAndDispatch(rule)`** —— 单一入口做"资格判断 + 防重复 + 派发"。`ReminderDispatchTask` 和 `ScheduledFlowRuleService` 共用：

```
┌─────────────────────────────┐
│ ReminderService             │
│   checkAndDispatch(rule)    │
│   - reminderEnabled?        │
│   - status 活跃?             │
│   - nextRunDate 在窗口内?    │
│   - 未发过?                  │
│   → 写 user_notice + 发邮件 │
└─────────────────────────────┘
         ▲              ▲
         │              │
┌────────┴────────┐  ┌──┴──────────────────────┐
│ Task 每天        │  │ Service createRule /    │
│ remind_time 扫  │  │ updateRule / startRule  │
│ 区间内所有规则   │  │ 末尾调一次              │
└─────────────────┘  └─────────────────────────┘
```

这样：
- 常规场景 → Task 每天 remind_time 扫
- **即时性补发**（用户新建规则时窗口已开启） → Service 里 create 完毕后立即调一次

| 失效挂钩：停用账户触发规则 status=5 + accountId=null | ✅ |

### 11.6 Bug #6 · updateRule 不清旧通知

**现象**

规则 14（每月 1 号房贷）的通知里写"将于 2026-04-24 09:00:00 自动记账"，但查规则 `nextRunDate=2026-05-03`。通知和规则对不上——**误导性通知**。

**根因**

`updateRule` 里 save 后只调用 `reminderService.checkAndDispatch` 补发新通知，但**没清旧通知**。用户改 `cycleDates` 后新旧 nextRunDate 不一致，旧通知残留。

**修复**

`updateRule` save 后加一行：

```java
// 规则字段改动后旧通知已过时，全清再补发
noticeRepo.deleteByRelatedRuleId(id);
reminderService.checkAndDispatch(saved);
```

### 11.7 Bug #7 · advanceCursor 错过分支不清旧 runDate 通知

**现象**

规则 next=4/24 runTime=09:00，今天 13:XX（已过 09:00）扫描器走分支 E "今天已过点"→ `advanceCursor(markExecuted=false)` → 推 next=5/3。但通知表里 `related_run_date=4/24` 的那条通知没被清掉，成了误导。

**根因**

原 `advanceCursor` 只在 `completed` 分支清通知：

```java
if (completed) {
    noticeRepo.deleteByRelatedRuleId(rule.getId());
}
```

错过路径（markExecuted=false）没清。

**修复**

记下旧 nextRunDate，推完后精确删那一天的通知：

```java
Date oldNextRunDate = rule.getNextRunDate();
// ... 推进 next / save ...
if (completed) {
    noticeRepo.deleteByRelatedRuleId(rule.getId());  // 全清
} else if (oldNextRunDate != null) {
    noticeRepo.deleteByRelatedRuleIdAndRelatedRunDate(
            rule.getId(), oldNextRunDate);  // 精确删旧那天
}
```

成功执行路径（`executeRuleOrThrow` 内部已经删过一次）走这里是幂等 no-op。

### 11.8 Bug #8 · 已执行过的规则改字段时 next_run_date 回退导致丢天

**现象**

每日规则 Day1 14:14 执行成功后 `last=today, next=明天`，用户 14:20 PUT 改 runTime=14:24。改完查规则 `next` 回退到**今天**。

扫描器下一分钟扫：
- `last=today == today` → 分支 A 跳过 ✅ 不重复扣
- 但明天 `next=昨天 < today` → 分支 B 推 next=后天 ❌ **跳过了明天那次**

旧逻辑下，用户**每 PUT 一次已执行规则，就少扣一天**。

**根因**

`baselineForRecompute` 公式只看 today 和 startDate，**忽略 `lastRunDate`**：

```java
// 旧：每日周期 from=today-1 → next=today（回退）
LocalDate base = startDate.isAfter(today) ? startDate : today;
return base.minusDays(1);
```

已执行过的规则应该以 `lastRunDate` 为下限（不能回退到 ≤ lastRunDate 的日期）。

**修复**

把 `lastRunDate` 加入 base 的 floor 运算：

```java
LocalDate anchor = startDate.isAfter(today) ? startDate : today;
LocalDate base = anchor.minusDays(1);
if (rule.getLastRunDate() != null) {
    LocalDate lastRun = toLocalDate(rule.getLastRunDate());
    if (lastRun.isAfter(base)) {
        base = lastRun;  // 用 lastRun 作为下限
    }
}
return base;
```

修后同场景：
- base = max(4/23, lastRun=4/24) = 4/24
- next = CycleCalculator(DAILY, 4/24) = 4/25 → **保持不动**
- 明天正常扣，不漏

## 十三、通知清理最终覆盖（七处）

随着三轮自测迭代，通知清理在 7 处触发点闭环。对用户而言"通知列表永远只显示还有意义的提醒"：

| 触发点 | 清理范围 | 代码位置 |
|---|---|---|
| 执行成功 | 删该规则该执行日 | `executeRuleOrThrow` |
| 规则删除 | 删该规则全部通知 | `deleteRule` |
| **规则更新**（#6 新加） | 删该规则全部通知 + 补发新的 | `updateRule` |
| 规则暂停 | 删该规则全部通知 | `pauseRule` |
| 规则失效（账户停用） | 删该规则全部通知 | `invalidateByAccount` |
| 规则失效（分类停用/归档） | 删该规则全部通知 | `invalidateByType` |
| 规则自然完成（到 end_date） | 删该规则全部通知 | `advanceCursor` SYS_COMPLETE 分支 |
| **扫描推游标**（#7 新加） | 删旧 runDate 的那条 | `advanceCursor` 错过分支 |

## 十二、通知全生命周期清理（第一版）

用户自测时提出："不想让用户看无意义的通知"。盘点了规则状态变化的所有场景，补齐 3 个清理点：暂停、失效（账户/分类）、自然完成。
