### 4. 🔴 OSIV + 双 ORM 死锁修复（重点）

#### 现象

用户调 `POST /system/config/autoExcel/runNow` 报：

```
HikariPool-1 - Connection is not available, request timed out after 30008ms
(total=1, active=1, idle=0, waiting=1)
```

调用栈定位到 `excelService.countMonthFlows` → `flowDao.getFlowByMain`（MyBatis）。

#### 根因

`AutoExcelExecuteService.runOnce()` 在同一方法内：

```java
configService.getTarget()              // ← JPA (AppConfigRepository)
excelService.countMonthFlows(month)    // ← MyBatis (FlowDao)
mailService.sendXxx(...)               // ← SMTP IO
noticeService.create(...)              // ← JPA (UserNoticeRepository)
configService.setLastRunDate(today)    // ← JPA
```

Spring Boot 默认 `spring.jpa.open-in-view=true`（OSIV）：

1. JPA 第一次查询时绑定一个 connection 到 thread，**持有到 HTTP 请求结束**才释放
2. MyBatis 后续调用申请连接时，**OSIV 已占用一个**，需要从池里另起一个
3. Hikari 当时池里只有 1 个连接（远端 MySQL），扩容到 max=5 时**新建连接超时**
4. 等 30s 报错

之前 `ExcelService.makeMonthExcel` 不报这个错纯属运气好（连接池有空闲 / 调用顺序不同）。

#### 修法

`AutoExcelExecuteService.runOnce()` 加 `@Transactional(rollbackFor = Exception.class)`：

```java
@Transactional(rollbackFor = Exception.class)
public void runOnce() { ... }
```

加事务后 Spring 把方法绑到一个事务上下文，JPA 和 MyBatis **共享同一个 connection**，不再各自申请。问题立即消失。

#### 副作用与 trade-off

- 事务里有 `mailService.sendXxx` 走 SMTP 网络 IO，事务时长包含网络延迟。可接受（< 几秒）；如果 SMTP 慢可考虑后续把发邮件改 `@Async` 或事件解耦
- runOnce 内部已 catch 所有异常吃下并转站内通知，正常路径事务总是 commit

#### 教训（记入 memory）

**项目级 recurring 坑**：用户提到"以前我就遇到过"。已记入：
- `memory/feedback_jpa_mybatis_transactional.md` —— 跨 Claude 长期记忆
- `feature-guide/config-ui-backend-design.md` §六风险与对齐 —— 后续后端 review 检查项

**预防性规则**：写新的同时调 JPA Repository + MyBatis Mapper 的 Service 方法时，**预防性加 @Transactional**，不等到 bug 出来才改。Code review 也按此规则扫。

### 7. 🔴 SQL 备份失败仍发空附件邮件 bug 修复

#### 现象

用户报：22:00 自动备份后收到一封"已备份"邮件，附件 0 字节。备份目录留下 `yd_jz_yyyyMMdd_HHmm.sql` 空文件。

#### 根因

旧代码 `SQLBackUpTask.doBackup()`：

```java
Process p = Runtime.getRuntime().exec(cmd);
p.waitFor();  // ← 拿到 exit code 但完全没检查
if (FileUtils.isExist(...)) { mailService.sendSqlBackup(...); }
```

shell 的 `>` 重定向**先创建空文件再跑命令**。mysqldump 失败时（远端 MySQL 当时不可用 / 认证失败 / 权限不足）：
- exit code != 0
- stderr 写错误
- 但 stdout 文件已被 shell 创建为 0 字节
- `FileUtils.isExist(...)` 返 true
- → 发空邮件

调试时手动跑 mysqldump 命令本身正常（92KB），证明命令没问题，是**远端 MySQL 那一刻不可用**（同时段也触发了 OSIV 死锁，根因相同）。

#### 修法

三重检查：

```java
StringBuilder stderrBuf = new StringBuilder();
try (BufferedReader reader = new BufferedReader(new InputStreamReader(p.getErrorStream()))) {
    String line;
    while ((line = reader.readLine()) != null) stderrBuf.append(line).append('\n');
}
int exitCode = p.waitFor();

if (exitCode != 0 || !backupFile.exists() || backupFile.length() == 0) {
    log.error("SQL 备份失败：exitCode={}, fileSize={}, stderr={}", ...);
    if (backupFile.exists() && backupFile.length() == 0) backupFile.delete();
    return;  // 不发邮件
}
```

- 读 stderr：mysqldump 错误信息走 stderr，不读会塞满 pipe 让子进程挂；读完也方便日志诊断
- 检查 exit code != 0
- 检查 0 字节文件（关键，shell `>` 重定向给的假象）
- 删除 0 字节占位文件，避免备份目录假阳性

### 8. 🔴 创建/更新/启动定时记账规则后即时补发提醒：账户/分类显示成"—"  bug v2

#### 现象

用户创建一条规则"咖啡"后立即收到提醒邮件，但邮件里：

```
账户    —
分类    —
```

#### v1 修复（昨天）失败原因

昨天我加了 `refetchWithAssociations()` 后调 `ruleRepo.findById()` 想触发 EAGER load。但 **JPA L1 cache 命中** —— 刚 save 的 entity 还在 EM 里，findById 直接返回那个缓存实例（associations 为 null），根本没去 DB 重读。

```java
// v1（坏的）：被 L1 cache 拦截
private ScheduledFlowRule refetchWithAssociations(ScheduledFlowRule saved) {
    return ruleRepo.findById(saved.getId()).orElse(saved);  // 返回缓存，account/type 仍是 null
}
```

#### v2 修法（今天）

放弃靠 JPA EAGER 自动加载，**显式查关联表 + Lombok setter set**：

```java
private ScheduledFlowRule refetchWithAssociations(ScheduledFlowRule saved) {
    if (saved.getAccountId() != null && saved.getAccount() == null) {
        accountRepo.findById(saved.getAccountId()).ifPresent(saved::setAccount);
    }
    if (saved.getTypeId() != null && saved.getType() == null) {
        typeRepo.findById(saved.getTypeId()).ifPresent(saved::setType);
    }
    if (saved.getActionId() != null && saved.getAction() == null) {
        actionRepo.findById(saved.getActionId()).ifPresent(saved::setAction);
    }
    if (saved.getAccountToId() != null && saved.getAccountTo() == null) {
        accountRepo.findById(saved.getAccountToId()).ifPresent(saved::setAccountTo);
    }
    return saved;
}
```

`@ManyToOne(insertable=false, updatable=false)` 只影响 JPA 持久化行为，不影响 Java setter（Lombok 生成的）。所以可以直接 set 关联实体。

ReminderDispatchTask 里每天扫描的提醒**不受这个 bug 影响**，因为它走 `ruleRepo.findRulesForReminder(...)` 是 fresh 查询，自动加载 EAGER 关联。

### 9. autoExcel 事后清理今日提前提醒通知

#### 背景

定时记账规则在执行成功后会 `noticeRepo.deleteByRelatedRuleIdAndRelatedRunDate(...)` 清当天的旧提醒。**但 auto_excel 没做这层** —— 5-1 21:00 执行后，4-28 那条"3 天后将生成"的旧提醒还会留在通知列表里跟"已生成"通知并排展示。

`UserNoticeService` 加 `deleteByTypeAndRunDate(...)` 包装。

`AutoExcelExecuteService.runOnce()` finally 块里加：

```java
Date todayAsDate = Date.from(today.atStartOfDay(ZoneId.systemDefault()).toInstant());
noticeService.deleteByTypeAndRunDate(NOTICE_TYPE_AUTO_EXCEL_REMIND, todayAsDate);
```

`runOnce()` 在 cron 触发时 today=runDate，正好清掉 (type=2, runDate=today) 那条旧提醒。手动 runNow 时 today != runDate，删 today 不会误删未来提醒。

### 10. 🔴 MySQL 端 stale 连接累积撞 max_connections 上限（基础设施层）

#### 现象

调用 `runNow` 死锁后，查 MySQL processlist 发现：

```
max_connections                = 10
Threads_connected              = 11   ← 已超
9 个 root@<本机外网 IP> Sleep（最老 1.6 小时）
```

11 个连接里 9 个是用户机器（外网 IP）的 Hikari/IDE/DBeaver/DevTools 历史漂浮 stale。**MySQL `wait_timeout=28800`（8 小时）才自动清**，开发期一上午积满 10 个名额。

#### 根因 1：服务端 my.cnf 极致瘦身

老配置（`Server/MySQL/my.cnf`）注释写"单用户、小数据库（<20MB）"，目标低内存：

```ini
innodb_buffer_pool_size=20M
max_connections=10
# 没设 wait_timeout, 默认 28800
```

#### 根因 2：客户端 Hikari 没 stale 防护

老配置只有 `maximum-pool-size=5 / minimum-idle=1`，没设 max-lifetime / keepalive-time，连接长期不旋转，stale 累积。

#### 修法（双层）

**MySQL 端 `Server/MySQL/my.cnf`**（用户升级 v2.7.0 后拉新镜像即生效）：

```ini
innodb_buffer_pool_size=64M           # 20M → 64M：把整个 yd_jz DB+索引缓存进内存
max_connections=30                    # 10 → 30：留余量给开发期 stale
wait_timeout=600                      # 默认 28800（8h）→ 600（10min）：主动清 stale
interactive_timeout=600
table_definition_cache=100            # 50 → 100
table_open_cache=100                  # 50 → 100
thread_cache_size=8                   # 2 → 8
sort_buffer_size=512K                 # 各种 buffer 翻倍
```

实际占用约 110MB（旧 ~46MB），**多 60MB 换稳定性**，开发机/普通 VPS 完全不痛。

**客户端 Server 三个 properties 全加**：

```properties
spring.datasource.hikari.max-lifetime=600000      # 10 分钟旋转，跟 MySQL wait_timeout 对齐
spring.datasource.hikari.keepalive-time=300000    # 5 分钟 ping 一次防 stale
spring.datasource.hikari.connection-timeout=5000  # 5s 拿不到连接立即失败（旧 30s 太长）
```

**逻辑双层防护**：
- Hikari 主动旋转 + 每 5 分钟 ping 让连接活着
- MySQL 兜底主动清 10 分钟无活动连接
- 两者协调：连接最多活 10 分钟就轮换，stale 累积不可能发生

## 遇到的坑 / 注意事项

### 1. OSIV 默认 true 是 Spring Boot 已知 anti-pattern

Spring Boot 团队多年来一直考虑改默认值但没做（兼容性顾虑）。社区共识是大型项目应该 `spring.jpa.open-in-view=false`。本项目混用 JPA + MyBatis，这个默认值就是个隐藏地雷。

短期修法：每个混用方法加 @Transactional。
长期方案：本特性发版后单独评估全局关 OSIV 的可行性（要扫所有 Controller 是否依赖 lazy load）。

### 2. HTML 邮件 inline 样式约束

不能用 `<style>` 标签或外部 CSS（Outlook / QQ 邮箱直接吃掉）。所有样式必须 `style="..."` 内联。table 布局更兼容（老 Outlook）。

### 3. base64 内嵌 logo vs cid 引用

两种方式邮件内嵌图片：
- **base64 data URI**：HTML 直接 `<img src="data:image/png;base64,...">`。简单，文件 ≤ 10KB OK
- **cid 引用 + multipart 附件**：`<img src="cid:logo">` + 邮件 attach with `helper.addInline("logo", ...)`。更兼容老客户端，但代码复杂

我选 base64（5.8KB 不大）。如果后续遇到客户端不显示图，再换 cid。

### 4. 测试发邮件别太勤

QQ SMTP 短时间发 8 封（testAll）虽没立刻限频，但用户连续 testAll 可能触发反垃圾。开发期 OK，生产前别按这个频率压测。

### 5. JPA L1 cache 让 findById 变成"不去 DB"

`save()` 后 `findById(savedId)` 不一定真去 DB —— Hibernate L1 cache（EntityManager scoped）会直接返回那个刚 save 的 in-memory 实例。`@ManyToOne(EAGER)` 也不会因为 findById 触发 fetch，因为 entity "已经在内存里"。

排查 ManyToOne 关联未加载的 bug 时不能假设 findById 会重新读 DB。要么 `entityManager.refresh(saved)`，要么 `em.detach + findById`，要么直接显式 `accountRepo.findById(...)` set 上去（最简单）。

### 6. shell 重定向陷阱

`mysqldump ... > file.sql` 通过 `cmd /c` 或 `/bin/sh -c` 执行时，**shell 先创建空文件再跑命令**。命令失败时文件已存在但 0 字节，光看"文件是否存在"会误判为成功。

正确判断三件事：
- 子进程 `exitCode != 0`
- 必须读 `process.getErrorStream()`（否则 pipe 塞满子进程挂；也能拿到错误信息）
- 文件大小 > 0

### 7. 远程 MySQL 连接池硬上限是隐藏地雷

服务端 `max_connections=10` + 客户端长连接 + 没 wait_timeout 控制 = stale 累积上限撞墙。开源项目最初为低内存设的极致瘦身参数，运行一段时间会让连接池耗尽，触发各种诡异错误（备份失败 / OSIV 死锁）。**必须 client 主动旋转 + server 主动清**，双层防护。

### v2.6.x → v2.7.0 升级 break change（重要）

1. **登录认证默认开启** —— 之前 `ENABLE_LOGIN=false`（env 默认）的用户升级后会被引导注册。可以在系统设置里关掉
2. **MySQL 容器内存配额提升** —— 新 my.cnf 实际占用约 110MB（旧 ~46MB），如果 docker-compose.yml 里手设过 `mem_limit: 128M`，请提到 256M
3. **8 个 env 失效** —— `webhook_url` / `cron.sqlBackupTime` / `auth.enable` / `auth.expired` / `auth.single_login` / SMTP_*（5 个）需要从 docker-compose.yml 删除
4. **WebHook 容器不再发布** —— 删除该容器，邮件配置在前端"系统设置 - 邮件"重填
5. **MySQL processlist 旧 stale 连接需要手动 kill 一次**（一次性）：升级前累积的 sleep 连接 wait_timeout 改成 600s 后会自动清，但首次升级建议 `KILL` 一遍

### `build.sh` 改动

- 移除 `easyaccounts-webhook` 构建项
- MySQL 镜像版本 bump（my.cnf 改了）
