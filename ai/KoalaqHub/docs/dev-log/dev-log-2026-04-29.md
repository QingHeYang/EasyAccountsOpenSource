## Part 2 · 结构化错误（issue #29）

### 协议

工具失败时不再返回裸字符串，而是 `ToolError`：

```json
{
  "code": "E_TYPE_DISABLED",
  "message": "分类已停用",
  "hint": "该分类已被停用。请重新调用 types 工具换一个未停用的分类。",
  "retryable": false,
  "metadata": {"http_status": 200, "backend_code": 42009, "backend_msg": "..."}
}
```

### 三层落地

1. **错误码定义**：新增 `koalaq_hub/tools/error_codes.py`
   - `ToolError` dataclass + `make_error()` 工厂 + `from_backend_response()` + `from_exception()`
   - 后端 BaseDto.code → AI 错误码的映射表
2. **工具内部接入**：
   - `tools/base.py` 的 `BaseTool._error()` 扩展支持 `code/message/hint/retryable/error_obj`，向后兼容旧 `error=str`
   - `tools/builtin/easy_accounts.py` 各工具改为 `_error(error_obj=...)` 风格，统一用 `_check_response()` 识别后端业务错误
   - `mcp/easyaccounts_server.py` 各工具改为 `_error_json()` 序列化为外部 MCP 客户端可读 JSON
3. **执行器 / 协议透传**：
   - `tools/executor.py`、`core/executor/tool_executor.py` 的所有失败路径包成 `ToolError`，结果项加 `error_object` 字段
   - `core/websocket_handler.py` 的 `MessageBuilder.create_tool_response_message` 增加可选 `error_object` 参数，写入 WS 消息的 `object.error_object`
   - `core/chat/base_chat_processor.py` 在转发工具结果到前端时透传 `error_object`

### 给前端的字段约定（请主管 Claude 派给前端 Claude）

WebSocket 消息中 `type=tool_response` 的负载结构：

```json
{
  "type": "tool_response",
  "status": false,
  "object": {
    "tool_call_id": "...",
    "tool_name": "add_flow",
    "tool_response": "...",          // 给 LLM 看的可读字符串
    "error_object": {                // 仅失败时存在；老消息可能没有此字段
      "code": "E_TYPE_DISABLED",
      "message": "分类已停用",
      "hint": "...",
      "retryable": false,
      "metadata": { ... }
    }
  }
}
```

前端建议：
- `status === false && error_object` 存在 → 渲染结构化错误气泡：标题用 `message`，副标题用 `hint`，按 `retryable` 显示「重试」按钮
- 几个特殊错误码值得跳转 UI：
  - `E_TYPE_DISABLED / E_TYPE_ARCHIVED / E_TYPE_HAS_CHILDREN` → 「去分类管理」
  - `E_ACCOUNT_DISABLED` → 「去账户管理」
  - `E_MAIL_NOT_CONFIGURED` → 「去配置邮件」
  - `E_AUTH_FAILED` / `E_NEED_REGISTER` → 跳登录 / 注册页
- 老消息（`error_object` 缺失）回退到展示 `tool_response` 字符串（兼容路径）

## Part 3 · 连锁问题修复

完成 Part 1+2 后，实际跑起来暴露出多个独立但相互掩盖的 bug。按时间顺序记录。

### 3.1 `'arguments'` KeyError —— LLM 残缺 tool_call

**现象**：科技云 GLM 偶发返回 `function: {"name": "current_date"}`，缺 `arguments` 字段。下游 `tc["function"]["arguments"]` 直接 `KeyError`，整个消息处理崩溃，前端卡住。

**根因**：流式累积逻辑（`enhanced_llm_client._handle_stream_function_calling`）只在 `delta.arguments` 非空时才创建 `arguments` key。某些 LLM 在无参函数调用时不发 arguments delta，导致最终 dict 缺 key。OpenAI 协议规定无参也得给 `"{}"`，但部分 LLM 不规范。

**修法**：
- `koalaq_hub/core/llm/enhanced_llm_client.py` 的 `_convert_tool_calls_list`：流式收口处过滤无 name 的 tool_call（无法执行），缺 arguments 兜底 `"{}"`
- `koalaq_hub/core/chat/base_chat_processor.py` 的 `_execute_tool_calls`：用 `.get()` 兜底，但**不丢弃** tool_call

### 3.2 「continue 跳过」会破坏 OpenAI 协议

**坑**：第一版我在 base_chat_processor 里发现缺 name 的 tool_call 直接 `continue`，结果发现这会破坏 LLM 历史 —— assistant 消息里已经写了所有 tool_call_id，少一个 tool_response 下一轮 LLM 调用直接 400。

**纠正**：
- 通读 `base_chat_processor` 后明确分工：上游 `_convert_tool_calls_list` 过滤干净（assistant 历史也只写过滤后的）；下游不丢任何 tool_call
- 通读 `history_manager.get_history` 发现末尾有「未匹配 tool_call 自动补 `[执行被中断]`」的最后兜底（行 496-513），所以即使下游漏写也不会 400，但 LLM 看到 `[执行被中断]` 体验降级

**三层防御协作关系**：

| 层 | 位置 | 职责 |
|----|------|------|
| 上游 | `_convert_tool_calls_list` | 过滤无 name 残缺 + 兜底 `arguments="{}"`，新数据干净落库 |
| 中游 | `_execute_tool_calls` | 信任上游，不丢任何 tool_call，所有失败走结构化错误 |
| 兜底 | `get_history` | 万一漏写 tool_response，补 `[执行被中断]` 保协议正确 |

### 3.3 历史污染回放 —— SQLite 里有脏 tool_call_raw

**现象**：3.1 出现时虽然流程崩溃，但 assistant 消息**已经在炸异常之前落库到 SQLite** 了（`messages.message_id=337`，`tool_call_raw` 缺 `arguments`）。修了上游过滤后**新数据**干净，但**存量脏数据**还在 DB，每次取历史都被原样发给 LLM API，触发 LLM 服务端 400。

**修法**：`koalaq_hub/core/history_manager.py` 的 `get_history()` 增加消费侧清洗 —— 构造发给 LLM 的 message_dict 之前，对历史 `msg.tool_calls` 中每个 `function` 做兜底：缺 `name` 丢弃这条 tool_call，缺 `arguments` 补 `"{}"`。脏数据不动（不破坏 SQLite），但发给 LLM 时干净。

### 3.4 DeepSeek-R1 thinking 协议要求传回 reasoning_content

**现象**：用户切到 DS-R1 模型后报 400 `The reasoning_content in the thinking mode must be passed back to the API.`

**根因**：旧的 `add_assistant_message` 故意不让内存版 message 带 reasoning_content（注释「保持对话历史干净」），仅 DB 版本保留。get_history 构造 LLM 请求时拿不到，于是不传给 LLM。但 DS-R1 协议强制要求所有历史 assistant 消息带回当时的 reasoning_content，否则拒绝。

**修法**：
- `core/history_manager.py` 的 `add_assistant_message`：内存版与 DB 版统一带 `reasoning_content`，去掉旧注释
- `get_history()` 构造 message_dict 时：assistant 消息（带 tool_calls 的和不带的两条分支）都把 `reasoning_content` 字段拼进去
- 不区分平台 —— OpenAI/智谱忽略未知字段，DS-R1 强制要

### 3.5 httpx timeout 配置错位

**现象**：用户调 flows 工具 5.5s 后报 E_TIMEOUT，但配置里 `tool_execution_timeout=60` 秒。

**根因**：`EasyAccountsClient` 内部用 `httpx.AsyncClient()` **未传 timeout**，跑的是 httpx 默认 5 秒。配置里的 60s 形同虚设。

**修法**：
- `EasyAccountsClient` 加 `self.timeout = config.tool_execution_timeout` + `async_client()` 工厂方法返回带 timeout 的 client
- 脚本批量替换所有 `httpx.AsyncClient()` → `client.async_client()`：内部工具 9 处 + MCP 8 处共 17 处

### 3.6 误判代理为问题（事故 + 自纠回退）

**现象**：3.5 修完后再调 flows 还是报 E_NETWORK。

**误判**：我以为后端在 `127.0.0.1:8083`（grep `.env` 时只看到一行 `EASYACCOUNTS_URL=http://127.0.0.1:8083`，没验证实际生效），加了 `trust_env=False` 让 httpx 绕过系统代理直连本地。

**真相**：用户配置的实际生效值是公网域名（远程后端），需要走代理才能访问。`trust_env=False` 把唯一可达路径堵死，直接 ConnectError。用户原话："你的网络肯定写错了，自行 review!"

**纠错过程**：
1. `python -c "from koalaq_hub.config.settings import config; print(config.easyaccounts_url)"` —— 才发现实际值不是我以为的那个
2. 让用户 curl 验证两组端口：直连不走代理拿到 401（说明后端在线），走代理反而失败 —— 证实直连可达，加 `trust_env=False` 是堵了正确路径
3. 立即回退两个文件的 `trust_env=False`

**教训**：已写进 memory `feedback_verify_config_in_process.md`：「配置类问题先在进程里 print 实际值，不要凭 .env 推断」。

### 3.7 `.env` 改了不生效 —— shell environ 残留压制

**现象**：用户改了 `.env` 的 `EASYACCOUNTS_URL`，但 KoalaqHub 进程实际读到的是更早的旧值（端口对不上）。

**根因**：`load_dotenv` 默认 `override=False`，遇到 `os.environ` 已存在的同名变量就不覆盖。用户 shell 里残留了旧值（最可能来源：conda env 的 `activate.d` 钩子），压制了 `.env`。

**尝试的修法**：在 `settings.load_env()` 加 `override=True` —— **被用户拦回退**（"settings 不能改"）。

**实际采用**：用户在启动 KoalaqHub 的 PowerShell 里手动清残留：

```powershell
Remove-Item Env:EASYACCOUNTS_URL -ErrorAction SilentlyContinue
python -m koalaq_hub
```

排查残留来源的命令：
```powershell
Get-ChildItem $env:CONDA_PREFIX\etc\conda\activate.d  # conda 钩子
[Environment]::GetEnvironmentVariable('EASYACCOUNTS_URL', 'User')  # 用户级永久
[Environment]::GetEnvironmentVariable('EASYACCOUNTS_URL', 'Machine')  # 系统级永久
notepad $PROFILE  # PowerShell profile
```

### 3.8 顺手修复 —— TypesTool 可用性逻辑

属于 Part 1 的 bug 修复，但单独记录：原代码仅看「有无子分类」，正确规则是「**有子分类 + 父分类自身 actionId 不为 null**」才不可用（通用容器型父分类 `actionId=null` 时可直接记账）。否则后端会返回 42002 `TYPE_HAS_CHILDREN`。

修在 `koalaq_hub/tools/builtin/easy_accounts.py` 的 `TypesTool.execute()` 与 `koalaq_hub/mcp/easyaccounts_server.py` 的 `types` 工具同步生效。
