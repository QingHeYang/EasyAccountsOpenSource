## 〇、立项背景

讨论中达成共识：项目内**该让用户在 UI 改的配置不应该用环境变量**。本版本一并解决两件事：

1. **邮件 SMTP 配置 UI 化** —— 同时干掉 WebHook 容器（已无存在必要）
2. **备份 cron 配置 UI 化** —— 让用户能在前端改备份时间

主线的 v2.7.0 不再延后这两件事，跟定时记账、连带修复一起发布。

## 一、子项 A · 邮件 SMTP UI 化（WebHook 内吸）

### 1.1 现状（事实）

- `WebHook/` 是独立的 Python FastAPI 容器（端口 8083）
- 仅承载邮件发送（SMTP），通过 `SMTP_*` 环境变量配置
- Server 通过 HTTP POST `/webhook` 调用，传文件 + 文件名 + 文件类型
- 当前事件类型：`sql_backup` / `month_excel` / `screen_excel` / `analysis_excel` / `scheduled_reminder`
- 这个独立容器**最初想做"用户可自定义钩子"**，但实际上从未有用户改过那 50 行 Python，定位从未兑现

### 1.2 产品目标

- **WebHook 容器在本版本起取消发布**，邮件发送能力**内聚到 Server**
- 用户在**前端 UI**配置 SMTP（服务器地址 / 端口 / 发件邮箱 / 发件密码 / 收件人列表）
- 全局开关由 UI 控制：是否发 SQL 备份邮件 / 是否发 Excel 邮件 / 定时记账提醒邮件按规则级 `emailEnabled` 控制（已有逻辑保留）

### 1.3 行为定义

- 修改 SMTP 配置后：**立即生效**，不需要重启
- 配置存储位置：复用 v2.7.0 已建的 `app_config` 表（基础设施已就绪）
- 邮件发送失败：**保持当前"失败即丢弃"行为**（不引入队列 / 重试），写一条错误信息到现有的 user_notice 或 server log（具体写到哪由开发 Claude 决定，这是技术方案）
- 大附件发送：维持当前能力，不针对超时做新增改造

### 1.4 老用户迁移路径

> 本节是产品规则，不是技术方案

- **直接断**：v2.7.0 起，老的 docker-compose 里的 WebHook 容器**可以直接删除**，发版时配套**升级指南**告诉用户：
  - 删 WebHook 容器
  - 在前端"系统设置"里重新填一次 SMTP 信息
- **不做兼容代码**（不让 Server 在没配 UI 时回退去调老 WebHook，那种代码维护成本不值）
- 升级指南里要给出"如何从 docker-compose env 复制现有 SMTP 配置过去"的人话操作步骤

### 1.5 镜像 / 部署

- `easyaccounts-webhook` Docker 镜像在本版本起**不再发布**
- Docker Hub / 阿里云上历史镜像保留（让老用户在升级前还能拉到 v2.6.x 的老镜像）
- `build.sh` 移除 webhook 构建项

## 二、子项 B · 备份 Cron 配置 UI 化

### 2.1 现状（事实）

- 备份调度由 `cron.sqlBackupTime` 配置驱动（默认 `0 0 22 * * ?` 即每晚 10 点）
- 当前来源：环境变量 `SQL_BACKUP_TIME` → 配置文件 → `@Scheduled(cron = "${...}")` 静态解析
- 后果：**用户改了配置必须 `docker-compose up -d` 重启容器才生效**
- 已有 `POST /backup` 手动触发接口，但**没有**修改备份时间的接口

### 2.2 产品目标

- 用户在**前端 UI**配置：
  - 备份时间（cron 表达式 / 或简化的"每天 HH:mm"，见 §2.4 待确认）
  - 是否启用自动备份开关
- 修改后：**立即生效**，无需重启容器
- 在 UI 上提供**手动触发一次备份**的按钮（这个能力后端已有，只需前端接入）

### 2.3 行为定义

- 配置存储位置：同样复用 `app_config` 表
- cron 表达式合法性校验：
  - 表单层做语法校验，非法不允许保存
  - 后端兜底再校验一次
- 自动备份关闭后，定时任务停止；手动触发仍可用
- 配置入库后老的环境变量 `SQL_BACKUP_TIME` 处理：
  - **首次升级时**：以现有环境变量值作为初始值写入 `app_config`
  - **后续**：忽略环境变量，以 `app_config` 为准

### 2.4 待用户拍板的产品问题

| # | 问题 |
|---|---|
| **B1** | UI 上展示给用户的形态：cron 表达式（极客友好，普通用户看不懂）/ 简化的"每天 HH:mm 时间选择器"（友好但牺牲灵活性）/ 两种切换 |
| **B2** | 用户填错 cron 表达式系统怎么处理：a) 表单拒绝保存；b) 保存后任务起不来时回退到上一个有效值；c) 两层都做 |
| **B3** | "自动备份开关"是否单独提供？还是"清空 cron 即关闭"作为隐式开关？ |

### 2.5 不在本版本范围（明确不做）

- 备份目录 UI 化（属于敏感系统路径，仍走环境变量）
- mysqldump 命令模板 UI 化（含密码，安全风险）
- 备份保留份数 / 自动清理（独立功能，归到后续版本）
- 多份备份策略（日 / 周 / 月不同保留），同上

## 三、各端交付目标（产品语言）

### 🟦 Server

1. **配置入库**：邮件 SMTP 配置、备份 cron 配置写入 `app_config` 表，提供读写接口
2. **邮件发送内嵌**：把当前 WebHook 干的事（按事件类型组装邮件 + 调 SMTP）内聚到 Server
3. **备份调度运行期可重读**：用户改了备份 cron 后，下一次按新表达式跑（不需要重启）
4. **首次升级时迁移**：从环境变量读初始值写入 `app_config`（之后该环境变量不再生效）
5. **删除 WebHook 模块**：`build.sh` 不再构建该镜像；项目里 `WebHook/` 目录可以保留只读历史，也可以整体删除（由开发 Claude 决定）

### 🟩 Web

1. **新增"系统设置"模块**（或在现有设置页加 Tab）
2. **SMTP 配置表单**：服务器地址 / 端口 / 发件邮箱 / 发件密码 / 收件人 / 各事件类型的全局开关
3. **备份配置表单**：备份时间（按 §2.4 确定形态）/ 自动备份开关 / 手动触发按钮
4. **配置项变更后即时反馈**："已保存"/"已生效"，不再需要"请重启容器"那种文案
5. **测试发送邮件按钮**（建议有，让用户配完立即知道有没有配对）

### 🟥 WebHook

**取消发布**。代码可以从仓库移除（建议保留 git 历史用于追溯）或冻结只读。

## 四、风险

| 风险 | 缓解 |
|---|---|
| 老用户升级时邮件突然不可用 | 升级指南里强调"必须在前端重新配 SMTP"，发布说明置顶 |
| 用户填错 cron 导致备份从此不跑 | 表单校验 + 后端兜底 + UI 显眼提示"下次备份预计在 XX" |
| SMTP 密码以明文存 DB | 后端实现时建议加密存储（这是技术方案，开发 Claude 自决，但这是底线提醒） |
| 备份配置改成立即生效后，调度机制要变 | 这件事会引入新调度方式，可能影响 v2.7.0 已有的"定时记账调度任务"。开发 Claude 评估后产出方案 |
