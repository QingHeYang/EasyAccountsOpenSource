## 一、这是什么功能

**定时记账**：让用户把周期性发生的真实账单交给系统代为记录。

**与快记模板本质不同**：定时记账是"真实发生的账单"（由系统代执行），必须字段齐全；快记模板是"预填辅助工具"，可字段不全。两者独立共存，v2.7.0 不做互转。

## 二、规则字段

### 2.1 必填字段

| 字段 | 说明 |
|---|---|
| 规则名称 | 用户给这条规则起的名字（例："房贷月供"） |
| **记账完整字段** | 金额、账户、分类、收支动作、备注、转账目标账户（转账时）等，对应系统现有 Flow 全部字段 |
| 周期类型 | 四种单选，见 §三 |
| 周期内具体日期 | 按周期类型多选或无须选，见 §三 |
| 账单发生时间 HH:mm | 指调度器启动的时间，每天到这个时分就尝试执行；系统内部精度到秒（默认 00） |
| 开始日期 | **必须 ≥ 今天 + 1 天**，不允许选今天或之前 |
| 是否提醒 | 关联 §七 的提醒功能 |
| 是否发送邮件 | **单条规则级别**的开关，用户决定哪条规则到期才发邮件（全局不另设此开关） |

### 2.2 选填字段

| 字段 | 说明 |
|---|---|
| 结束日期 | 不填即永久 |

### 2.3 系统填充字段

| 字段 | 说明 |
|---|---|
| 是否永久 | 用户没填结束日期时，系统自动标记 |
| 创建时间 | 系统写入 |
| 状态 | 按 §四 自动流转 |

## 三、周期类型与日期选择

**四种周期互斥（单选）**，选定后按该周期内的规则挑具体日期：

| 周期 | 日期选择 | 示例 |
|---|---|---|
| **每日** | 无需选 | 每天都执行 |
| **每周** | 多选（周一 ~ 周日） | 每周一 + 周四 |
| **每月** | 多选（1 ~ 31 号） | 每月 1 号 + 15 号 |
| **每年** | 多选（MM-DD 具体日期） | 每年 3-1 + 10-1 |

### 月末边界
- 每月 / 每年选到"31 号"或"2-30"这类无效日期时 → **回退到该月的最后一天**
- 多日期场景同规则（比如每月选 1 + 31 号，遇到 2 月就是 1 号和月末那一天）

### 未来执行日预览
- **每月 / 每年**：展示下个月 / 下一年的执行日期（按多选出来的日期数量）
- **每日 / 每周**：不展示（没有意义）

## 四、状态与状态流转

### 4.1 五种状态

| 状态 | 含义 | 能否执行 |
|---|---|---|
| **未开始** | 已创建，但还没到开始日期 | ❌ |
| **开始** | 到了开始日期，按周期正常执行 | ✅ |
| **暂停** | 用户主动暂停 | ❌ |
| **完成** | 已到结束日期 | ❌ |
| **失效** | 系统因主数据失效自动标记 | ❌ |

### 4.2 状态流转

| 源 → 目标 | 触发方 | 条件 |
|---|---|---|
| 未开始 → 开始 | 系统 | 到达开始日期 |
| 开始 → 完成 | 系统 | 到达结束日期 |
| 开始 → 暂停 | 用户 | 用户点"暂停" |
| 开始 → 失效 | 系统 | 规则引用的账户/分类失效（见 §5.3） |
| 暂停 → 开始 | 用户 | **用户基于当前记录重新编辑 → 点"开始"** |
| 完成 → 开始 | 用户 | **用户修改开始日期（与必要字段）→ 点"开始"** |
| 失效 → 开始 | 用户 | **用户补齐失效字段 → 点"开始"** |

### 4.3 核心原则 —— 所有"恢复"都是手动的

**无论从哪个非执行态回到"开始"，都必须：用户基于当前记录进入编辑 → 修改相关字段 → 主动点"开始"按钮**。系统不做任何自动恢复。

## 五、执行规则

### 5.1 正常执行

1. 到达执行日 + 到达 HH:mm 时间 → 系统生成一条流水
2. 流水带 **定时记账专属来源标记**（写入 Flow 的 `from` 字段特殊值；同时备注里也追加标记，保持视觉可识别）
3. 推进下次执行日

### 5.2 不补漏 —— 全面性原则

任何错过都**不补**：

| 场景 | 行为 |
|---|---|
| 服务器停机期间错过执行日 | 启动后直接推进下次执行日，不补执行 |
| 启动时发现今天 HH:mm 已过 | 跳过今天的，等下次 |
| 启动时 HH:mm 未到 | 正常等待执行 |
| 运行期执行失败（非主数据类） | 写执行记录 + 推进下次执行日 + 状态保持"开始" |

### 5.3 主数据失效与规则失效

**触发失效的主数据变化**（与系统现有能力对齐）：

| 主数据 | 现有状态机制 | 触发规则失效 |
|---|---|---|
| 账户 | 有"停用"，**不能删除** | 账户被停用 → 引用它的规则进入"失效" |
| 分类 | 有"停用" + "归档"，**不能删除** | 分类停用或归档 → 引用它的规则进入"失效" |
| 收支动作 | **无状态变更、不能删除** | — 无失效触发 |

### 5.4 运行期失败分两类

| 失败类型 | 举例 | 系统行为 |
|---|---|---|
| **主数据类** | 账户停用、分类停用/归档 | 写执行记录（失败 + 原因） + 规则进入"失效" |
| **其他类** | 非负债账户余额不足 / 代码异常 / 偶发 bug | 写执行记录（失败 + 原因） + 推进下次执行日 + 状态保持"开始" |

**共同点**：任何失败都 **不重试、不补记**。

### 5.5 主动保护

账户被停用、分类被停用/归档的那一刻，系统**顺带**把引用它们的规则标为"失效"（不等到下次执行时才发现）。

## 六、信息记录表（执行日志 · 事后）

### 6.1 表的定位

每一次调度执行后写一条记录，用于**审计 + 用户查看历史**。一次失败只产生一条记录（不会刷屏）。

### 6.2 每条记录要能让用户看到的信息

- 属于哪条规则
- 执行时间
- 是否成功
- 成功时：关联生成的流水（可点击跳转到该流水）
- 失败时：失败原因文字（金额不足 / 账户停用 / 分类归档 / 代码异常 等）

### 6.3 用户入口

用户在定时记账详情页或独立的历史记录页查看（UI 细节后续定）。

---

## 七、信息提醒（事前 N 天）

### 7.1 全局配置（规则无关的一份配置）

| 字段 | 说明 |
|---|---|
| 提醒前 N 天 | N ∈ [1, 5]，**不支持当天提醒**（当天发无意义） |
| 提醒时间 | **全局统一**一个时间，**不允许**每条规则单独设置（否则用户会烦） |

### 7.2 每条规则级别的开关

| 字段 | 说明 |
|---|---|
| 是否提醒（per-规则） | 用户决定这条规则是否要提醒 |
| 是否发送邮件（per-规则） | 用户决定这条规则是否要额外发邮件 |

### 7.3 提醒送达方式

- **站内**：写入"信息通知"页面（面向用户的消息中心）
- **邮件**：若用户勾选"发送邮件" → 同时发邮件（依赖 WebHook 配置；未配置时在设置处给弹窗提示）

### 7.4 事前与事后的关系

- **事前**：§七 信息提醒
- **事后**：§六 信息记录
- **两张独立的表/概念**

### 7.5 后补需求（本版本已登记，不强制一次做完）

- 执行过后，把对应那条**提醒通知自动删除**（避免用户看到"N 天后要记"的过期提醒）

## 八、各端交付目标（产品语言）

### 🟦 Server（后端）

1. **规则管理**：新增、修改、查询、删除定时规则
2. **五态管理**：按 §四 状态机管理规则生命周期
3. **调度执行**：到达执行日 + HH:mm 时，系统自动按规则生成流水
4. **启动时跳过过期**：服务启动时已过的执行不补，直接推进
5. **失败处理**：按 §5.4 两类分别写执行记录 + 必要时置为失效
6. **主动保护**：账户停用、分类停用/归档时，同时把引用规则标为失效
7. **恢复时基于用户编辑**：任何状态要回到"开始"，都需要用户先编辑过才允许
8. **执行记录**：每次执行写一条信息记录，含成功/失败、关联流水、原因
9. **事前提醒**：按全局配置 + 规则级开关，执行日前 N 天的"提醒时间"触发一条站内通知；若该规则勾选"发邮件"，同时发邮件
10. **来源标记**：生成的流水 `from` 字段写入定时记账专属值，备注里追加可视化标记
11. **未来执行日预览**：每月 / 每年类型的规则，能返回其未来一轮的执行日期

### 🟩 Web（前端）

1. **设置页新增"定时记账"入口**（桌面 + 移动双端）
2. **规则列表**：展示名称、简要信息、周期、状态；五种状态视觉区分
3. **规则创建 / 编辑表单**：
   - 全字段必填校验（除明确可选项外）
   - 周期类型单选 + 日期多选（按类型切换 UI）
   - HH:mm 时间选择
   - 开始日期不允许选今天或之前
   - "是否提醒" + "是否发邮件"的 per-规则开关
4. **未来执行日预览**：每月 / 每年类型展示下个月 / 下一年的执行日期
5. **状态操作**：
   - "开始"按钮：仅在编辑过后允许点击（未开始 / 暂停 / 完成 / 失效 都走同一逻辑）
   - "暂停"按钮
   - **不提供**"立即执行一次"按钮
6. **失效状态的引导**：规则进入失效时，UI 明显提示哪个字段失效了
7. **流水列表标识**：定时记账生成的流水在列表上有明显来源标签
8. **信息记录（执行历史）查看**：展示每条规则的历史执行结果，失败可看原因，成功可跳转关联流水
9. **全局提醒配置入口**：提醒前 N 天 + 提醒时间，一次设置全局生效
10. **信息通知页面**：展示事前提醒通知（执行过后该提醒自动消失——后补需求）
11. **邮件依赖提示**：用户勾选"发邮件"但 WebHook 未配置时，弹窗提醒

### 🟥 WebHook

邮件通知由提醒功能调用（当用户规则勾选"发邮件"时）。

### AI 端 —— **本版本不做**

## 十、风险

| 风险 | 缓解思路 |
|---|---|
| 月末 / 闰年边界计算错 | 验收时专项覆盖 |
| 用户长期停机 | 明确不补漏 |
| 主数据状态变更触发失效 | 三类主数据的状态事件要全部接上规则失效逻辑 |
| 运行期其他失败持续产生记录 | 暂不做自动暂停（待观察） |
| 用户误把快记模板当定时记账 | UI 创建时文案强调差异 |
| HH:mm 粒度下启动时判断错过 vs 未过 | 业务规则明确"过了就不补，没过就执行" |
| 多日期场景下月末回退的预期歧义 | 明确规则：任何无效日期一律回退到月末 |

## 十一、待用户拍板的剩余产品问题

前轮问答已消化大部分产品歧义。剩余：

1. **版本号抬升时机** —— 什么时候把 `application-server.properties` 的版本号从 2.6.1 调到 2.7.0

3. **产品命名** —— 继续叫"定时记账"，还是改叫"周期账单"或其他（影响前端文案统一）
4. **其他类失败持续刷记录** —— 是否对连续 N 次失败的规则自动暂停（倾向不做，让执行记录自然累积让用户发现；如果做，N 取多少）
