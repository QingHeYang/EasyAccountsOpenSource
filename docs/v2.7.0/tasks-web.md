# v2.7.0 · Web 前端任务拆分

> 创建时间：2026-04-23
> 分支：`2.7.0`
> 文档性质：**产品级任务清单**（由主管给前端 Claude 下发），每包为一个可独立验收的交付单元
> 技术方案（组件结构、状态管理、路由等）由前端 Claude 自行设计，主管不出技术指引

---

## 使用说明

1. 每个任务包描述的是"用户能看到什么 / 做什么"，**不约束**前端如何实现
2. 每包含"验收条件" —— 达到即算完成
3. 依赖列出前置任务包或后端接口是否就绪
4. 优先级 P0/P1/P2，建议按优先级批次推进（见最后的里程碑）

## 📦 包 W1 · 规则管理基础

**用户价值**：让用户能在 App 里完成定时记账规则的"建、看、改、删、启停"全流程。

**交付内容（用户能看到 / 做到的）**：
- 设置页菜单里出现"定时记账"入口（桌面 + 移动双端）
- 点击进入后能看到规则列表（展示：规则名称、简要信息、周期、状态）
- 有一个明显的"新建规则"按钮
- 新建 / 编辑表单能填入所有规则字段：
  - 规则名称
  - 记账完整字段（金额 / 账户 / 分类 / 收支动作 / 备注 / 转账目标账户）
  - 周期类型单选（每日 / 每周 / 每月 / 每年）
  - 周期内日期选择（按类型切换 UI：每周多选周几 / 每月多选日期 / 每年多选 MM-DD）
  - 账单发生时间 HH:mm
  - 开始日期（必须 ≥ 今天+1，UI 上阻止选更早）
  - 结束日期（可留空）
  - 是否提醒（规则级开关）
  - 是否发送邮件（规则级开关）
- 列表项可点击"暂停"/"开始"（按钮态跟随状态切换）
- 可编辑、可删除规则

**验收**：
- 用户可以完整走一遍"新建一条每月定投规则 → 在列表看到 → 编辑修改金额 → 暂停 → 恢复 → 删除"流程，无任何阻塞
- 开始日期控件**不允许**选择今天或更早
- 周期切换时，对应的日期选择 UI 正确切换

**依赖**：后端规则 CRUD + 启停 API 就绪

**优先级**：P0

## 📦 包 W2 · 五态的视觉表达 + 失效引导

**用户价值**：用户一眼能看出哪条规则在跑、哪条出问题、为什么出问题。

**交付内容**：
- 规则列表上"未开始 / 开始 / 暂停 / 完成 / 失效"五种状态有**明显区分**（颜色、徽章、图标均可，前端自决）
- **失效状态**特殊处理：
  - 醒目地在规则卡片/行上提示"哪个字段失效了"（例如"账户'工商卡'已被停用"）
  - 提供一键进入编辑的入口
- "开始"按钮的启用/禁用：
  - 未开始 / 暂停 / 完成 / 失效 → 必须用户**编辑过一次**才能点"开始"
  - 正在"开始"状态下 → 按钮切为"暂停"
- "立即执行一次"按钮 —— **不做**（产品决策）

**验收**：
- 后端返回不同状态的规则时，列表视觉表达正确
- 失效规则点"开始"被拦截；编辑保存后"开始"可点
- 完成/暂停/失效的规则想恢复必须走编辑路径

**依赖**：W1 完成 + 后端状态返回正确

**优先级**：P0

---

## 📦 包 W3 · 未来执行日预览

**用户价值**：让用户在创建/编辑规则时预判"这规则设对了吗"。

**交付内容**：
- 仅在"每月 / 每年"类型的规则表单里展示未来执行日预览
- 每月类型：展示**下一个月**的执行日期（若多选，全部列出）
- 每年类型：展示**下一年**的执行日期（若多选，全部列出）
- 每日 / 每周不展示（意义不大）
- 周期配置变化时，预览实时刷新

**验收**：
- 用户配"每月 1、15、31 号"，能看到下月三个执行日（2 月会自动显示 28/29 日取代 31 号）

**依赖**：后端预览 API 就绪（W1/W2 可并行，不阻塞）

**优先级**：P1

---

## 📦 包 W4 · 流水列表识别定时来源

**用户价值**：用户在日常看流水时，一眼看出这条是"系统代记"的，不是自己手记的。

**交付内容**：
- 流水列表（桌面 + 移动双端）中，由定时规则生成的流水**展示一个明显的来源标签**（跟现有 `ai` / `mcp` / `Claw` 标签同构；颜色前端自定）
- 备注文字末尾带有定时记账的文字标识（后端已写入，前端只负责展示）

**验收**：
- 混合流水列表中，用户能快速筛出/识别定时来源的流水

**依赖**：后端生成流水时 `from` 字段已写入定时记账专属值

**优先级**：P0（与 W1 差不多同等重要，因为用户一开始用就会产生这类流水）

## 📦 包 W5 · 执行记录查看（信息记录表 UI）

**用户价值**：让用户能审计每条规则的执行历史，失败时能看到原因。

**交付内容**：
- 每条规则有"查看执行历史"入口（可以是规则详情页的一个 Tab，或列表项的一个按钮，前端自决）
- 历史列表展示：执行时间、是否成功、关联流水（成功时）、失败原因（失败时）
- 成功的记录能点击跳转到对应的流水详情
- 按时间倒序排列

**验收**：
- 用户能查看任意规则的完整执行历史
- 成功记录可跳转流水；失败记录能读到明确的原因文字

**依赖**：后端信息记录表 + 查询 API

**优先级**：P1

---

## 📦 包 W6 · 信息通知页面 + 事前提醒

**用户价值**：用户在规则到期前能被提醒，避免错过确认/余额准备。

**交付内容**：
- 新增"信息通知"页面（独立入口或整合到消息中心，前端自决）
- 显示所有事前提醒通知（哪条规则、几天后要执行、执行的金额/账户/分类）
- 通知条目可点击跳转到对应规则详情
- **全局提醒配置**入口（单独一处设置，不在每条规则里重复）：
  - "提醒前 N 天" (N ∈ 1~5)
  - "提醒时间"（一个时分）
- 用户在规则表单里勾选"发送邮件"但系统未配置 WebHook 时，弹窗提示"需先配置邮件通知服务"并给出跳转入口

**验收**：
- 到了提醒日的指定时间，用户能在"信息通知"页看到对应条目
- 全局配置修改后，所有规则的提醒策略都按新配置走

**依赖**：
- 后端事前提醒触发 + 通知写入（消息表由用户另行设计完成）
- 后端 WebHook 配置状态查询接口

**优先级**：P1

## 📦 包 W7 · 用户教育文案

**用户价值**：避免用户误把定时记账当快记模板用、造成意外扣账。

**交付内容**：
- 新建规则表单顶部 / 保存按钮附近，显著文字提示："定时记账到期后会**真实生成一笔流水**，与快记模板不同，请确认所有信息"
- 快记模板和定时记账的菜单入口文案 / 图标明确区分
- 文案内容由主管 Review（前端出初稿）

**验收**：
- 小白用户第一次看到两个功能，不会混淆

**依赖**：无

**优先级**：P1（随 W1 同步做完最好）

---

## 📦 包 W8 · 后补 · 执行后清除对应事前提醒

**用户价值**：避免"本月 1 号房贷记账"的提醒在执行后还一直挂在通知页。

**交付内容**：
- 规则执行成功后，对应的"还有 N 天"提醒通知自动消失（前端被动展示，后端会清理，前端只需在用户刷新/访问通知页时看到最新状态）

**验收**：
- 规则执行后，通知页不再显示该规则这个周期的提醒

**依赖**：后端实现"执行后清理关联提醒"

**优先级**：P2（后补需求，时间允许再做）

## 🗓 建议里程碑

| 里程碑 | 任务包 | 产品价值 |
|---|---|---|
| **M1 · 最小可用** | W1 + W4 + W7 | 用户能建规则、规则能真记账并被识别、不会误用 |
| **M2 · 状态完整** | W2 + W3 | 用户能看懂规则状态、能预判执行计划 |
| **M3 · 可审计** | W5 | 用户能查执行历史、排查失败原因 |
| **M4 · 提醒就位** | W6 | 用户在执行前被提醒到 |
| **M5 · 锦上添花** | W8 | 通知页自动清理 |

> 建议：前端 Claude **在开工前**用自己的 Web/dev-log 补一份"技术方案说明"，描述打算怎么实现（组件结构、状态管理、路由、接口调用）。主管 Review 后再开工。

## 🔗 跨端接口协作

前端开发需要后端提供：
- 规则 CRUD + 启停 API
- 状态字段正确返回
- 未来执行日预览 API
- 信息记录查询 API
- 事前提醒通知数据（从消息表读）
- WebHook 配置状态查询

**任一接口契约不明确 → 前端 Claude 先向主管反馈，由主管拉齐后端 Claude 对齐，再开始开发**。
