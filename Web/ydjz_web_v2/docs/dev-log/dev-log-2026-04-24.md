## 今日开发内容

### 1. API 层对接

#### 需求背景

v2.7.0 后端新增 `/scheduledFlow/*` 和 `/notice/*` 两组接口（OpenAPI 导出见 `docs/api/openapi.json`），需要前端注册对应类型 + API 对象。`UserNotice` 的 `ruleName` 在规则被删后返回 `"[已删除]"`，flowId / failCategory / failReason 均可为 null。

#### 解决方案

两个独立模块文件放在 `shared/api/`，跟随现有风格（`const enum` + `interface` + `export const xxxApi = { method() {...} }`）。

#### 关键代码

```ts
// shared/api/scheduledFlow.ts
export enum CycleType { DAILY = 1, WEEKLY = 2, MONTHLY = 3, YEARLY = 4 }
export enum RuleStatus { NOT_STARTED = 1, RUNNING = 2, PAUSED = 3, FINISHED = 4, INVALID = 5 }
export enum FailCategory { MASTER_DATA = 1, OTHER = 2 }

// cycleDates 在后端是 JSON 字符串，按 cycleType 解释。提供工具函数，让业务层用数组：
export function parseCycleDates<T extends number | string = number | string>(
  cycleDates: string | null | undefined
): T[] {
  if (!cycleDates) return []
  try {
    const parsed = JSON.parse(cycleDates)
    return Array.isArray(parsed) ? (parsed as T[]) : []
  } catch { return [] }
}

export function stringifyCycleDates(dates: Array<number | string>, cycleType: CycleType): string {
  if (cycleType === CycleType.DAILY) return '[]'  // DAILY 固定返回空数组
  return JSON.stringify(dates)
}
```

关键决策：
- `cycleDates` 类型保持 `string`（JSON 原串透传），不在 API 层做隐式解码，业务层显式调用 `parseCycleDates<number>(...)` / `parseCycleDates<string>(...)`，泛型由调用方指定。
- `NoticeType` 只有 `SCHEDULED_REMINDER = 1`，后续新增类型（回收站、AI 错误等）往 enum 里加 case 即可，前端按 type 分 icon / 跳转。

### 3. 周期配置 & 未来预览（W3）

#### 四种周期的日期选择 UI

- DAILY：无需选日期
- WEEKLY：7 格"周一~周日" pill 多选（存 `number[]` 1-7）
- MONTHLY：1-31 七列网格多选（存 `number[]`）
- YEARLY：MM-DD 标签列表 + "添加日期"按钮 → 弹月份 × 12 + 日期 × N 的选择器（存 `string[]`）

#### 未来执行日预览

每月 / 每年类型下方显示"下个月/下一年执行日"，纯前端算（不调 previewRule API）：

```ts
const futureRunDates = computed<string[]>(() => {
  const f = form.value
  if (f.cycleType === CycleType.MONTHLY && f.cycleDatesMonthly.length) {
    const nextMonth = new Date(new Date().getFullYear(), new Date().getMonth() + 1, 1)
    const y = nextMonth.getFullYear()
    const m0 = nextMonth.getMonth()
    const maxDay = new Date(y, m0 + 1, 0).getDate()  // 该月实际天数
    const uniq = new Set<string>()
    for (const d of f.cycleDatesMonthly) {
      uniq.add(`${y}-${pad2(m0 + 1)}-${pad2(Math.min(d, maxDay))}`)  // 月末回退
    }
    return [...uniq].sort()
  }
  // ... YEARLY 同理
})
```

选 `previewRule` 不调的理由：新建模式没 id；编辑模式下 API 基于已保存状态，用户改动没保存就看不到新预览。客户端算跟后端算法一致（闰年 + 月末回退），用户改配置实时看到结果。

### 4. 启停流程（W2）

#### 产品约束

- 未开始 → 开始：系统自动（到达 `startDate`）
- 开始 → 完成：系统自动（到达 `endDate`）
- 开始 → 暂停：用户点"暂停"
- 开始 → 失效：系统自动（主数据停用/归档）
- 暂停 / 完成 / 失效 → 开始：**用户必须编辑过一次才能重新启动**

#### UX 设计

不用"edited" 客户端 flag（刷新会丢），直接让点"开始"按钮进入编辑流程：

```ts
async function onToggleRuleStatus(rule: ScheduledFlowRule) {
  if (rule.status === RuleStatus.NOT_STARTED) return  // 未开始态没按钮
  if (rule.status === RuleStatus.RUNNING) {
    // 暂停直改
    await scheduledFlowApi.pauseRule(rule.id)
  } else {
    // 暂停 / 完成 / 失效 → 先让用户编辑确认，保存时顺带启动
    pendingStartAfterSave.value = true
    await onRuleClick(rule)  // 打开编辑对话框
  }
}

// onSubmit 里：
if (pendingStartAfterSave.value) {
  await scheduledFlowApi.updateRule(id, params)
  await scheduledFlowApi.startRule(id)  // 顺带启动
}
```

编辑对话框在此模式下：
- 标题改"确认并启动规则"
- 顶部加橙色 banner："保存后系统将自动启动此规则"
- 提交按钮文字改"保存并启动"

#### 未开始态的特殊处理

按钮位置显示灰色 pill：`🕐 2026-04-27 自动启动`，不带任何点击行为 —— 用户看到后就知道"等到那天系统会帮我启动"。同时在 `onToggleRuleStatus` 里 early return 拦截这个状态，防止后续模板误改触发 API。

## 遇到的坑 / 注意事项

### 1. `cycleDates` 表单内部结构

后端 DTO 用 `cycleDates: string`（JSON），但业务层按周期类型分成三个独立数组字段：

```ts
interface FormState {
  cycleDatesWeekly: number[]   // WEEKLY 专用
  cycleDatesMonthly: number[]  // MONTHLY 专用
  cycleDatesYearly: string[]   // YEARLY 专用
}
```

切换 cycleType 时全清空、提交时只取对应数组编码。避免类型 union 泄露到整个表单。

### 2. 编辑模式要 find 对象而不是只传 ID

`selectedAction` / `selectedAccount` 不能只存 ID（业务里要读 `handle` / `exempt` / `accountType` 等）。必须 await Promise.all 拉完列表后 `.find()`。加了竞态保护：

```ts
if (!formDialogVisible.value || editingRuleId.value !== rule.id) return
```

防止用户快速点不同规则导致串行污染。

### 3. `startDate` 测试期临时放开

产品规则 `startDate >= 今天+1`。为便于测试临时改为 `>= 今天`。三处都打了 `TODO(测试期放开)` 注释，grep 能一次找回：

```bash
grep -r "TODO(测试期放开)" src/
```

发版前必须恢复。

### 4. emoji 标签的配色陷阱

初版给 🦞 / ⏰ emoji 配实色背景（粉 / 橙），视觉很糊 —— emoji 自带多彩，跟实色底"两种颜色打架"。改成中性底 + 淡色描边解决。

后来 `⏰` 被用户叫停（觉得丑），定时改成纯文字"定时"+ 青色实底，因为纯文字（白）跟实色底不冲突，回到了 AI / MCP 的同一套样式。

### 5. `previewRule` API 不调的决策

后端的 `previewRule(id)` 需要已保存的规则 ID。新建模式没 id，编辑模式下 API 基于已保存状态 —— 用户改配置没保存就看不到新预览。所以改成**前端计算**，跟后端的"月末回退 + 闰年处理"对齐。两边算法要保持同步。

### 6. FlowEditor 的 z-index 叠加

初版"点查看流水 → 关日志对话框 → 开 FlowEditor"，用户反馈希望同时存在。改成"直接开 FlowEditor 覆盖日志对话框"，依赖 Element Plus PopupManager 自动 z-index 递增。目前测试无问题，但如果以后出现层级错乱，可能需要给 FlowEditor 显式传 `:z-index="3000"`。

### 7. `ruleName === '[已删除]'` 的斜体处理

后端规则删除后，日志里 `ruleName` 返回硬编码 `"[已删除]"`。前端做硬编码字符串匹配显示斜体灰字：

```vue
<span :class="{ 'log-rule-deleted': log.ruleName === '[已删除]' }">
```

有点 fragile（后端改串就挂），但当前够用。后续如果后端加独立字段 `ruleDeleted: boolean` 更稳。

### 8. Element Plus icon 按需导入

本次用到的图标：Plus / AlarmClock / ArrowRight / Close / Document / Refresh / Clock / Bell / InfoFilled / Setting / Tickets / CircleCheckFilled / CircleCloseFilled / Delete / VideoPlay / VideoPause / View / Calendar / Check。都是 `@element-plus/icons-vue` 导出，按需 import，不引入包级别开销。
