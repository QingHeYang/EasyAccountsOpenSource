### 2. 路由污染 bug 修复（最大的坑）

#### 现象

新建 / 编辑规则保存成功后跳到列表，列表点返回，**回到了刚才的新建 / 编辑页**而不是设置主页。

#### 根因

项目自维护了一套 `routeHistory` store（`shared/stores/routeHistory.ts`），`router.afterEach` 把每次导航都 push 进去 —— **push 和 replace 不区分**。

栈情况追踪：

```
进入路径：/setting → /setting/scheduled-flow → /setting/scheduled-flow/add
栈：[setting, list, add]
submit → router.replace 到 list → afterEach push list（重复不 push）
栈：[setting, list, add]   ← add 还在
列表点返回 → smartBack 'setting' → pop list → 栈顶 add → replace 到 add ❌
```

#### 解决方案

给 `routeHistory` store 加通用 `removeWhere(predicate)`：

```ts
// shared/stores/routeHistory.ts
function removeWhere(predicate: (path: string) => boolean) {
  history.value = history.value.filter(p => !predicate(p))
}
```

`ScheduledFlowAdd.vue` 抽个 helper，submit / delete 跳转前调用：

```ts
function pruneAddEditHistory() {
  routeHistory.removeWhere(
    (p) =>
      p.startsWith('/setting/scheduled-flow/add') ||
      p.startsWith('/setting/scheduled-flow/edit')
  )
}

// onSubmit 末尾
pruneAddEditHistory()
router.replace('/setting/scheduled-flow')
```

修复后追踪：

```
栈：[setting, list, add]
submit → pruneAddEditHistory() 清掉所有 add/edit 路径
栈：[setting, list]
→ router.replace 到 list（重复不 push）
栈：[setting, list]
列表点返回 → smartBack 'setting' → pop list → 栈顶 setting → replace 到 setting ✅
```

为什么用 `removeWhere` 而不是 `remove(route.fullPath)`：边缘情况下用户可能在多个 add/edit 路径间跳，或带不同 query（`?start=1` vs 无），一次性把模式匹配的全清更稳。

### 3. W3 未来执行日预览（移动端）

桌面端 v2.7.0 已有，移动端 ScheduledFlowAdd 表单里也加一份。算法跟桌面端对齐 —— `new Date(y, m, 0).getDate()` 取真实月末天数，`Math.min(d, maxDay)` 月末回退，闰年自动处理：

```ts
const futureRunDates = computed<string[]>(() => {
  const f = form.value
  const now = new Date()
  if (f.cycleType === CycleType.MONTHLY && f.cycleDatesMonthly.length) {
    const next = new Date(now.getFullYear(), now.getMonth() + 1, 1)
    const y = next.getFullYear()
    const m0 = next.getMonth()
    const maxDay = new Date(y, m0 + 1, 0).getDate()
    const uniq = new Set<string>()
    for (const d of f.cycleDatesMonthly) {
      const actual = Math.min(d, maxDay)
      uniq.add(`${y}-${pad2(m0 + 1)}-${pad2(actual)}`)
    }
    return Array.from(uniq).sort()
  }
  if (f.cycleType === CycleType.YEARLY && f.cycleDatesYearly.length) {
    const nextYear = now.getFullYear() + 1
    const uniq = new Set<string>()
    for (const mmdd of f.cycleDatesYearly) {
      const m = Number(mmdd.substring(0, 2))
      const d = Number(mmdd.substring(3, 5))
      if (!m || m < 1 || m > 12) continue
      const maxDay = new Date(nextYear, m, 0).getDate()
      const actual = Math.min(d, maxDay)
      uniq.add(`${nextYear}-${pad2(m)}-${pad2(actual)}`)
    }
    return Array.from(uniq).sort()
  }
  return []
})
```

UI 嵌在周期 cell-group 末尾的 inline-cell，浅绿底 + 绿色描边 pill 列。每改配置实时刷新。

#### 未读数共享 store

新建 `shared/stores/notice.ts`：

```ts
export const useNoticeStore = defineStore('notice', () => {
  const unreadCount = ref(0)
  const loaded = ref(false)

  async function refresh() {
    try {
      const res = await noticeApi.list({ isRead: false })
      unreadCount.value = (res.data.data ?? []).length
      loaded.value = true
    } catch (err) {
      if (!isHandledError(err)) unreadCount.value = 0
    }
  }

  function decrementUnread(delta = 1) {
    unreadCount.value = Math.max(0, unreadCount.value - delta)
  }

  function clearUnread() {
    unreadCount.value = 0
  }

  return { unreadCount, loaded, refresh, decrementUnread, clearUnread }
})
```

Board 和 Setting 都用 `noticeStore.unreadCount` 显示徽章；NotificationCenter 操作时 `decrementUnread / clearUnread` 乐观更新，避免每次操作等 refresh。

## 遇到的坑 / 注意事项

### 1. 自维护 routeHistory 的"push/replace 不区分"陷阱

**项目自维护了一套 history**（不是浏览器原生 history），`router.afterEach` 把每次导航都 push 进去。意思是：
- `router.replace` 不会从自维护栈里删掉旧条目，它跟 `router.push` 在自维护栈里一样
- "submit 后 replace 跳列表"这种常见模式会导致栈里残留 add/edit 路径

**任何**"提交后跳列表"的页面都要注意这个。这次给 `routeHistory` 加了通用的 `removeWhere(predicate)`，未来类似模式可以复用。

是否要在 dev-guide 里单独写一篇路由管理（之前问过用户，待定）。

### 2. 编辑模式回填的竞态保护

`Promise.all` 加载完依赖后必须再次校验路由没切走：

```ts
if (editingId.value !== id) return
```

否则用户快速点不同规则跳来跳去会出现"看到旧规则数据 + 部分新规则数据"的混合污染。

### 3. van-list 的 onLoad 自动触发

`van-list` 挂载后会自动触发首次 `onLoad`（除非 `immediate-check=false`）。所以 `onMounted` 里**不要**再手动调一次 `fetchPage`，否则会加载两次第 0 页。筛选切换时手动调是因为 van-list 的自动触发时机不可预测。

### 4. keep-alive 下用 onActivated，不是 onMounted

Board 和 Setting 都被 `<keep-alive>` 包裹（`mobile/layouts/HomeLayout.vue` 里 `<router-view v-slot> <keep-alive>...</keep-alive> </router-view>`），`onMounted` 只在第一次挂载时触发。用户从通知中心返回时要刷新未读数，得用 `onActivated`。

### 5. vant 的 `required` 把星号放在前面

vant `<van-field required>` 会在 label 前加红星。如果项目其他地方用的是 `cell-title-required` 类（::after 加在尾部），就要避开 `required` 属性，用 `#label` slot 接管渲染，否则同一个表单里星号位置不一致。

### 6. vant 4 没有 outline 铃铛

`bell` 只有实心版本（没有 `bell-o`）。需要 outline 铃铛只能：
- inline SVG（本次的方案）
- 引第三方图标库（不值得）
- 用近似的 vant outline 图标如 `volume-o`（喇叭）—— 视觉上不像通知

inline SVG 最稳，用 `currentColor` 跟样式联动。

### 7. 通知文案要砍

第一稿写 7 条覆盖所有清理场景，用户反馈"简化简化简化，有些不必说明"。文案不是越全越好，按"用户实际会困惑的场景"取舍。

### 8. svg stroke-width 的取舍

最初用 `2`，用户觉得粗，调到 `1.5`（heroicons outline 默认）。如果还想更细，`1.25` 是极限 —— 再细在 22px 尺寸下 antialiasing 会糊。
